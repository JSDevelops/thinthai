## ข้อสรุป

โครงการเป็นต้นแบบที่มีระบบหลังบ้านและธุรกรรมบางส่วนเชื่อม PostgreSQL แล้ว แต่ยังไม่พร้อมเปิดรับการจองและเงินจากลูกค้าจริง จุดเร่งด่วนคือทำให้หน้าจอทุกช่องทางใช้ธุรกรรมเดียวกัน เชื่อมระบบออนไลน์ให้ครบ และทำวงจรการจอง/ชำระเงิน/ยกเลิกให้ตรวจสอบได้
คง Next.js + NestJS + PostgreSQL และโครงสร้าง monorepo เดิม ใช้ API ที่แบ่งโมดูลชัดเจนในระบบเดียวก่อน ยังไม่มีเหตุผลจากผลวัดให้แยก microservices หรือฐานข้อมูลตามจังหวัด

## ขอบเขตและหลักฐาน

- อ่านโค้ดเว็บ API Flutter การตั้งค่า deployment, migrations, CI และชุดทดสอบ
- ตรวจ TypeScript ของ API และเว็บด้วย --noEmit --incremental false: ผ่าน
- รัน npm test: ชุดกฎสิทธิ์ 4/4 ผ่าน
- ครั้งนี้ไม่ได้รัน integration กับฐานข้อมูล, browser E2E, Flutter tests, load test หรือ production build ใหม่ ผลเก่าใน VALIDATION.md ไม่ถือเป็นการรับรองเวอร์ชันปัจจุบัน
- ลิงก์ Vercel ที่ได้รับเปลี่ยนไปหน้า Login Vercel จึงไม่ได้ยืนยันหน้าจอหรือธุรกรรมของ deployment นั้น และยังไม่ยืนยันว่า deployment ใช้ commit เดียวกับโฟลเดอร์นี้
- การตรวจนี้เป็นการอ่านโค้ดและทดสอบเฉพาะที่ระบุ ไม่ใช่การรับรองความปลอดภัยหรือการตรวจเจาะระบบ
- ไม่เปลี่ยนโค้ดธุรกิจหรือข้อมูลลูกค้าในการตรวจครั้งนี้

## สิ่งที่มีแล้วและควรเก็บไว้

- เว็บและหลังบ้านใช้ Next.js; API ใช้ NestJS; มี migrations PostgreSQL
- บัญชี/session, บทบาท USER/MERCHANT/ADMIN/SUPER_ADMIN และขอบเขตร้าน/จังหวัดตรวจฝั่งเซิร์ฟเวอร์
- สมัครผู้ประกอบการ ตรวจคำขอ จัดการร้าน สินค้า ราคา สต๊อกและรูป
- API คำสั่งซื้อและการจองมี transaction, การล็อกแถว และ request key กันรายการซ้ำ
- มีประวัติสถานะและข้อมูลราคาขณะสั่ง/จอง
- ตะกร้าเว็บเพิ่ม localStorage แล้ว ต่างจากรุ่นก่อนที่ตะกร้าหายเมื่อเปลี่ยนหน้า
- มี GitHub Actions สำหรับ formatting, typecheck, unit, build และ dependency audit
- มีหน้า Flutter หลายส่วนและชุดทดสอบ state แต่ยังเป็นข้อมูลจำลอง

### P1 — ก่อนเปิดนำร่องเชิงธุรกิจ

4. Worker ยังเป็นโครงสร้างเริ่มต้น ไม่มีตัวประมวลผลจริง: ต้องทำหมดอายุการกันที่นั่ง/สต๊อก แจ้งเตือน retry และติดตามงานล้มเหลว
5. CI ยังไม่เรียก test:integration หรือ browser E2E: เพิ่มฐานข้อมูลทดสอบแยกและทดสอบเส้นทางหลักก่อน deploy
6. localStorage ตรวจเพียง Array.isArray: เพิ่ม schema/version/ขีดจำกัดจำนวน แก้ข้อมูลเสีย และโหลดราคา/สต๊อกล่าสุดก่อนซื้อ ทดสอบออกจากระบบ/สลับบัญชี/เปิดหลายแท็บ
7. ปุ่มภาษาใน public-header.tsx ยังไม่มี action และลิงก์ ?cat=กิจกรรม / ?cat=ที่พัก ยังไม่เชื่อมตัวกรองที่อ่านจาก URL ใน trips-client.tsx; หมวดที่พักต้องมีแบบข้อมูลและเส้นทางจองเฉพาะก่อนแสดงว่ารองรับ
8. SSR ทริปคืน [] เมื่อ API ผิดพลาด: แยกหน้าว่างจริงจากระบบล่ม มี retry และบันทึก error; จำนวนที่นั่งต้องตรวจใหม่ตอนเลือกรอบและยืนยัน
9. ยังต้องทำยืนยันอีเมล กู้รหัสผ่าน MFA ผู้ดูแล การจัดการอุปกรณ์/session และตรวจเจ้าของร้านตามขั้นตอนธุรกิจ
10. ข้อมูลชุมชน รูป รีวิว ป้าย Verified และตัวเลขผลกระทบต้องมีแหล่งที่มาและขั้นตอนตรวจรับ อย่านำตัวเลขจำลองไปแสดงเป็นผลจริง

### P2 — เมื่อเริ่มมีผู้ใช้และข้อมูลเพิ่ม

11. รายการหลายจุดจำกัด 100 รายการ: เพิ่ม pagination/filter/search ฝั่ง API ไม่กรองเฉพาะรายการที่ส่งมาในหน้า
12. รูปสินค้าอยู่ใน bytea: แยก media ไป object storage/CDN เมื่อพร้อม เก็บ metadata/สิทธิ์/เจ้าของใน DB และมีงานย้ายไฟล์ที่ตรวจย้อนกลับได้
13. มี store-level lock ในธุรกรรม: รักษาความถูกต้องไว้ก่อน ทดสอบ load และวัดการรอล็อกก่อนลดขอบเขตล็อก
14. เอกสารบางส่วนบอกแอปสมบูรณ์ทั้งที่ยัง mock: ทำตารางสถานะ feature ให้ตรงโค้ดและผลทดสอบ

## แผนพัฒนาเป็นเฟส

ระยะเวลาเป็นกรอบวางแผนสำหรับนักพัฒนา 2 คน มี QA และผู้ดูแลผลิตภัณฑ์ร่วมงาน ต้องปรับจากผลเฟส 0 ไม่ใช่กำหนดส่งตายตัว การอนุมัติบัญชีชำระเงินและ onboarding ผู้ประกอบการอาจใช้เวลาเพิ่ม

### เฟส 0 — ยืนยันฐานโครงการและขอบเขตรุ่นแรก (2–3 วัน)

งาน: จับคู่ commit กับ deployment, ตรวจทุกปุ่ม/เส้นทางว่า mock หรือจริง, จัด backlog P0/P1/P2, ระบุเจ้าของงาน, แยก dev/staging/production, กำหนดพื้นที่นำร่องและรูปแบบรายได้
รุ่นแรกที่แนะนำ: ทริปชุมชนและสินค้าของฝากใน 1–2 จังหวัด พร้อมหลังบ้าน อาหารส่งทันทีและที่พักเป็นโมดูลเปิดภายหลัง
ส่งมอบ: feature matrix, แผนผังข้อมูล, รายการจุดเสี่ยง, acceptance criteria และ release checklist
ผ่านเมื่อ: ทีมระบุได้ว่าทุกฟีเจอร์ใช้แหล่งข้อมูลใด และอะไรอยู่/ไม่อยู่ในรุ่นแรก

### เฟส 1 — เชื่อมระบบให้ใช้งานออนไลน์ครบวงจร (1–2 สัปดาห์)

งาน: API_ORIGIN เดียวตาม environment; frontend บน Vercel เชื่อม NestJS ที่ deploy จริง; PostgreSQL ที่สำรองข้อมูลได้; HTTPS/session/origin; แยก test credentials; health/error logs; ปิดหรือเชื่อมการจองจำลองหน้าแรก; ทดสอบ deployment ใหม่; CI รัน integration/E2E
ส่งมอบ: staging ที่แยกข้อมูลจาก production และทำรายการได้จากนอกเครื่องพัฒนา
ผ่านเมื่อ: USER/MERCHANT/ADMIN/SUPER_ADMIN ผ่านเส้นทางหลักและ negative permission tests; ข้อมูลอยู่หลัง restart; rollback ได้; ทดสอบกู้ข้อมูลได้

### เฟส 2 — สมาชิก ผู้ประกอบการ และเนื้อหาจริง (2–3 สัปดาห์)

งาน: ยืนยันอีเมล/กู้รหัสผ่าน/MFA admin; โปรไฟล์และ session; ตรวจผู้ประกอบการ; ขอบเขตจังหวัด-อำเภอ-ตำบลตามหน้าที่; CRUD ชุมชน สถานที่ กิจกรรม itinerary สิ่งที่รวม/ไม่รวม จุดนัดพบและช่องทางติดต่อ; media ที่มีสิทธิ์; รองรับไทย/อังกฤษและเลือกภาษาเอง
ส่งมอบ: ชุมชนและทริปจริงที่ผ่านการตรวจ พร้อมผู้รับผิดชอบและเงื่อนไข
ผ่านเมื่อ: เจ้าของร้านดูแลเฉพาะข้อมูลตนเอง ผู้ดูแลพื้นที่ไม่เข้าถึงนอกเขต เนื้อหาที่เผยแพร่มีผู้รับผิดชอบ ผู้ใช้กลับจาก login แล้วทำรายการเดิมต่อได้

### เฟส 3 — ธุรกรรม การรับเงิน และรายได้ผู้ประกอบการ (3–4 สัปดาห์)

งาน: แยกสถานะ booking/order, payment และ refund; กำหนดกันที่นั่ง/สต๊อกหมดอายุ; worker; ปรับตะกร้าให้ทนข้อมูลเก่า; ใบสรุปราคาจริง; payment provider ที่รองรับธุรกิจ; signed webhook; ป้องกัน event ซ้ำ/สลับลำดับ; รับมือเงินเข้าหลังเวลาจองหมด; ยกเลิก/คืนเงิน; ledger ค่าธรรมเนียมและยอดจ่ายร้าน; รายงานกระทบยอด; แจ้งเตือนและ support
ส่งมอบ: จอง/ซื้อ → จ่าย → ยืนยัน → ใช้บริการ/ส่งมอบ → ยกเลิกหรือคืนเงิน → กระทบยอด ครบวงจรใน sandbox ก่อน live
ผ่านเมื่อ: ไม่ oversell, ไม่ตัดยอดซ้ำ, ไม่จ่ายร้านซ้ำ, webhook ปลอมถูกปฏิเสธ, เครือข่ายขาดแล้วกลับมาดูผลเดิมได้, จำนวนเงินตรงรายงานผู้ให้บริการ
นโยบายคืนเงิน เงื่อนไขผู้ให้บริการ และเอกสารลูกค้าต้องให้เจ้าของธุรกิจ/ผู้เชี่ยวชาญที่เกี่ยวข้องตรวจตามรูปแบบดำเนินงานจริง

### เฟส 4 — เปิดนำร่องแบบจำกัดพื้นที่ (2–3 สัปดาห์)

งาน: onboarding ผู้ประกอบการกลุ่มเล็ก; ทดสอบมือถือ/แท็บเล็ต/คอมพิวเตอร์และอินเทอร์เน็ตช้า; accessibility/ข้อความผิดพลาด; privacy และการจัดการข้อมูล; บัญชี support; monitoring/alerts; load test; restore drill; คู่มือเหตุขัดข้องและ rollback; ตรวจความปลอดภัยก่อนเปิดเงินจริง
ส่งมอบ: pilot ใน 1–2 จังหวัดพร้อมทีมดูแลปัญหาและ dashboard
ผ่านเมื่อ: ไม่มีบั๊กร้ายแรงด้านเงิน/สิทธิ์/การจอง กู้ข้อมูลจาก backup ได้ ทุกรายการเงินกระทบยอดได้ และผู้ประกอบการทดลองทำงานได้โดยไม่ต้องพึ่งนักพัฒนา
กำหนดตัวเลข SLO/RPO/RTO และจำนวน concurrent users ร่วมกับทีมตามยอดใช้งานคาดการณ์ก่อนทดสอบ ไม่ใช้จำนวนผู้ใช้ที่เดาเป็นคำรับรอง

### เฟส 5 — มือถือและการเติบโต (2–4 สัปดาห์ขึ้นไป)

งาน: Flutter เชื่อม API/session จริง; secure token storage ตามรูปแบบ auth ที่ออกแบบสำหรับ mobile; deep link/push; บุ๊กมาร์กข้ามอุปกรณ์; ตั๋ว QR ตรวจจากเซิร์ฟเวอร์และกันเช็กอินซ้ำ; SEO รายทริป/ชุมชน; sitemap; รีวิวเฉพาะผู้ใช้บริการ; referral/promotion ที่มีงบและเกณฑ์; analytics funnel
ส่งมอบ: เว็บและมือถือใช้ข้อมูลและกฎธุรกิจชุดเดียวกัน
ผ่านเมื่อ: จองบนมือถือเปิดดูบนเว็บได้ สถานะตรงกัน logout/session หมดอายุทำงานถูก และไม่แสดงคำสั่งซื้อที่ cache ไว้ข้ามบัญชี
ทำ native release หลัง API และธุรกรรมเสถียร เพื่อลดการแก้สองชุดพร้อมกัน

### เฟส 6 — ขยายบริการและปริมาณข้อมูล (ต่อเนื่องตามผลวัด)

งาน: อาหารส่งทันที (เวลาร้าน โซน/พิกัด ค่าส่ง รับงาน ติดตามส่งมอบ); ที่พัก (ห้อง/คืน/จำนวนผู้เข้าพัก/availability/ราคา); พื้นที่โปรโมทและ moderation; ค้นหาเร็วขึ้น; geospatial/PostGIS เมื่อต้อง query พื้นที่; CDN/cache; connection pooling; load tuning; read replica/partition เมื่อมีปัญหาที่วัดได้
ผ่านเมื่อ: แต่ละโมดูลมีรายได้/ต้นทุนและเจ้าของงานชัด ผ่านสิทธิ์และ load test ของตัวเอง เปิด/ปิดแยกพื้นที่ได้โดยไม่กระทบทริปและสินค้าทั่วไป
สำคัญ: โซนจัดส่งใช้เฉพาะอาหารส่งทันที ทริป กิจกรรมทำอาหาร และสินค้าส่งพัสดุไม่ถูกบังคับด้วยกฎโซนเดียวกัน

## โครงสร้างเทคโนโลยีที่แนะนำ

- เว็บ/หลังบ้าน: Next.js เดิม แยกหน้า customer/workspace ตามการใช้งาน ใช้ design tokens ร่วมกับ Flutter
- API: NestJS เดิม แยกโมดูล Identity, Merchants, Communities/Content, Catalog, Orders, Trips/Bookings, Payments/Ledger, Delivery, Notifications, Audit
- สัญญา API: OpenAPI และ schema ที่ตรวจ runtime; สร้าง client สำหรับ TypeScript/Dart เพื่อลดชื่อฟิลด์ไม่ตรงกัน
- ฐานข้อมูล: PostgreSQL, migration ที่ตรวจย้อนหลังได้, constraints/indexes, เงินเป็นจำนวนเต็มหน่วยสตางค์, เวลา UTC และแสดงตาม timezone, สำรองและซ้อมกู้คืน
- ไฟล์: object storage/CDN; DB เก็บข้อมูลอ้างอิงและสิทธิ์ ไม่เก็บ secrets ใน frontend
- งานเบื้องหลัง: เริ่ม durable outbox/job ใน PostgreSQL หรือเลือก queue ที่ทีมดูแลได้; retry/dead-letter/dedup เป็นข้อบังคับของงานที่กระทบเงิน/สต๊อก
- ภาษา: ใช้ภาษาที่ผู้ใช้เลือกก่อน แล้วภาษาที่ browser ส่งมา แล้ว fallback ไทย/อังกฤษ ไม่ต้องใช้ AI เดาภาษาอุปกรณ์
- AI: เพิ่มภายหลังเพื่อช่วยแปล/สรุป/ค้นหา โดยราคาที่นั่งและเงื่อนไขต้องอ่านจากข้อมูลจริง ไม่ใช้ข้อความ AI เป็นแหล่งยืนยันการจอง

## ฐานข้อมูลที่ต้องเพิ่มตามเฟส

เฟส 2: communities, places, media_assets, content_translations, email_verifications, password_resets และ scopes ตามระดับพื้นที่ที่ต้องใช้จริง
เฟส 3: reservation_holds, payment_attempts, payment_events (provider event ID unique), refunds, ledger_entries, payouts, outbox_jobs; เพิ่ม policy version/snapshot ให้รายการที่ยืนยันแล้ว
เฟส 5: reviews (โยงรายการที่ใช้บริการ), bookmarks, checkins, notification_preferences และ promotion attribution
เฟส 6: delivery_jobs/zones/fees, accommodation_units/rate_plans/room_inventory แยกจาก trip departures
ไม่ต้องสร้างทุกตารางก่อนมีฟังก์ชัน ใช้ migrations เพิ่มทีละเฟสและมีแผนย้ายข้อมูล/ตรวจยอด

## งาน 10 รายการแรกที่ควรเปิดเป็น issue

1. ยืนยัน commit และ environment ของ deployment จริง
2. แก้ API rewrite และ configuration ตรวจ startup
3. เชื่อมปุ่มจองหน้าแรกกับ trip/departure จริง
4. แยก empty/error และทำ retry ที่ไม่สร้างรายการซ้ำ
5. ตรวจ schema ตะกร้าและทดสอบ refresh/login/switch-account
6. เพิ่ม integration/E2E และฐานข้อมูลทดสอบใน CI
7. ยืนยันอีเมล กู้รหัสผ่าน และ MFA admin
8. เพิ่มหมดอายุ hold พร้อมทดสอบแข่งกับ payment webhook
9. ทำข้อมูลชุมชน/ทริปจริงและการตรวจผู้ประกอบการ
10. เตรียม payment sandbox, reconciliation, backup restore และ pilot checklist

## วิธีส่งต่องานให้ง่ายต่อการพัฒนา

ทุก issue ระบุผลลัพธ์ผู้ใช้, role, ขอบเขตข้อมูล, API/schema ที่เปลี่ยน, acceptance tests, migration/rollback และผู้รับผิดชอบ
ทุกเฟสอัปเดต feature matrix, OpenAPI, schema diagram, runbook และ CHANGELOG ให้ตรงกับโค้ด
Definition of Done: ผ่าน code review/CI, ทดสอบสิทธิ์เชิงลบและ error cases, มี monitoring ที่จำเป็น, คู่มือผู้ใช้ตรงพฤติกรรม และผู้รับผิดชอบธุรกิจตรวจรับ
