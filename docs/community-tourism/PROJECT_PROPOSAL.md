# โครงการพัฒนาแพลตฟอร์มท่องเที่ยว วัฒนธรรม และตลาดชุมชน

ข้อเสนอโครงการและแผนเทคโนโลยีเพื่อพัฒนาและขยายบริการ

ฉบับ 1.0 วันที่ 4 ตุลาคม 2569

จัดทำสำหรับเจ้าของโครงการ ทีมพัฒนา และผู้ร่วมดำเนินงานชุมชน

เอกสารนี้เสนอการสร้างแพลตฟอร์มตัวกลางที่เชื่อมการค้นพบชุมชน การจองบริการ การซื้อผลิตภัณฑ์ และการโปรโมทไว้ในระบบเดียว พร้อมแผนบุคลากร เทคโนโลยี ฐานข้อมูล การทดสอบ และลำดับพัฒนา เพื่อใช้กำหนดขอบเขตและขอประเมินราคาอย่างเป็นระบบ

ข้อเสนอหลักคือใช้ Next.js และ TypeScript สำหรับหน้าบ้าน ใช้ NestJS บน Node.js สำหรับระบบหลังบ้าน และใช้ PostgreSQL ร่วมกับ PostGIS เป็นฐานข้อมูลธุรกรรมและพิกัด ออกแบบเป็นระบบแบ่งโมดูลชัดเจนตั้งแต่ต้น แล้วเพิ่มระบบค้นหา แคช และฐานข้อมูลรายงานเมื่อผลการใช้งานบ่งชี้ว่าจำเป็น

กรอบดำเนินงานที่เสนอคือ 40 สัปดาห์สำหรับเวอร์ชันเต็มระยะแรก โดยเปิดทดลองธุรกรรมในสัปดาห์ที่ 25 ถึง 28 ภายใต้ทีมและขอบเขตที่ระบุในเอกสาร ตัวเลขโหลด งบประมาณ และตัวชี้วัดเป็นสมมติฐานเพื่อวางแผน ต้องยืนยันด้วยการสำรวจ ประเมินราคา และทดสอบก่อนใช้เป็นข้อผูกพัน

### ข้อมูลโครงการที่ต้องเติม

ชื่อแบรนด์ หน่วยงานเจ้าของโครงการ ผู้รับผิดชอบ จังหวัดและชุมชนนำร่อง งบที่อนุมัติ และวันเริ่มโครงการจริง ยังต้องกำหนด ระยะเวลาทั้งหมดจึงนับจากวันเริ่มโครงการ ไม่ผูกกับวันเปิดบริการที่ยังไม่ได้ตกลง

### โครงสร้างเอกสาร

บทที่ 1 ถึง 4 อธิบายเหตุผล เป้าหมาย ขอบเขต และการดำเนินบริการ บทที่ 5 ถึง 13 ครอบคลุมเทคโนโลยี สถาปัตยกรรม ฐานข้อมูล ความปลอดภัย และคุณภาพ บทที่ 14 ถึง 18 ระบุ Roadmap ทีม งบประมาณ ความเสี่ยง และเกณฑ์ตรวจรับ ภาคผนวกเป็นรายการงานและแหล่งอ้างอิงสำหรับทีมพัฒนา

## 1 หลักการและเหตุผล

ชุมชนสามารถนำเสนอคุณค่าผ่านสถานที่ วิถีชีวิต อาหาร งานฝีมือ และประสบการณ์ที่คนในพื้นที่เป็นผู้จัด การสร้างช่องทางกลางที่เชื่อมข้อมูลเหล่านี้กับบริการและสินค้า จะช่วยให้ผู้สนใจเปลี่ยนจากการอ่านเรื่องราวไปสู่การวางแผนเดินทาง จองกิจกรรม หรือซื้อผลิตภัณฑ์ได้ต่อเนื่อง

ปัญหาที่โครงการตั้งใจตรวจสอบและแก้ไข ได้แก่ ข้อมูลกระจายอยู่หลายช่องทาง ราคาหรือวันว่างไม่เป็นปัจจุบัน การรับคำสั่งซื้อผ่านข้อความทำให้ติดตามยาก และผู้ขายไม่มีภาพรวมรายรับกับผลการโปรโมท ประเด็นเหล่านี้เป็นสมมติฐานของโครงการ ต้องสัมภาษณ์ผู้ประกอบการและนักท่องเที่ยวในพื้นที่นำร่องเพื่อจัดลำดับความสำคัญก่อนพัฒนา

แพลตฟอร์มจะให้แต่ละชุมชนมีพื้นที่เล่าเรื่องของตนเอง และให้ผู้ประกอบการมีหน้าร้านที่จัดการสินค้า บริการ และธุรกรรมได้ ขณะที่ผู้ดูแลมีเครื่องมือตรวจสอบเนื้อหา รับเรื่องร้องเรียน และติดตามการชำระเงิน การออกแบบจึงต้องให้ความสำคัญกับทั้งประสบการณ์ลูกค้าและการทำงานจริงของคนในชุมชน

ข้อมูลจะเติบโตหลายลักษณะพร้อมกัน ได้แก่ รายการสินค้า รอบกิจกรรม การจอง การชำระ รูปภาพ และประวัติการใช้งาน จึงต้องแยกข้อมูลธุรกรรมที่ต้องถูกต้องทันทีออกจากข้อมูลสำหรับค้นหา วิเคราะห์ และไฟล์ขนาดใหญ่ การแยกหน้าที่นี้ช่วยให้ขยายระบบได้โดยไม่ทำให้การจองและการชำระเงินช้าตามขนาดคลังภาพหรือรายงาน

### หลักการดำเนินโครงการ

- ชุมชนมีสิทธิ์ตรวจเรื่องราว ภาพ และข้อมูลวัฒนธรรมของตนก่อนเผยแพร่
- ผู้ซื้อเห็นราคา เงื่อนไข ผู้ให้บริการ และช่องทางช่วยเหลือก่อนยืนยันรายการ
- การจอง การซื้อ การคืนเงิน และรายรับต้องตรวจสอบย้อนหลังได้
- หน้าจอรองรับมือถือ อินเทอร์เน็ตช้า และผู้ขายที่มีทักษะดิจิทัลแตกต่างกัน
- การขยายเครื่องและฐานข้อมูลอิงผลวัดจริง พร้อมกำหนดต้นทุนและผู้ดูแล

ผลที่คาดหวังคือเกิดช่องทางเข้าถึงลูกค้าและจัดการงานที่เป็นระบบ สามารถวัดยอดขาย การใช้บริการ และการกระจายรายรับได้ โดยไม่อ้างว่ารายได้ชุมชนจะเพิ่มขึ้นในสัดส่วนใดก่อนมีผลทดลองจริง

## 2 วัตถุประสงค์ กลุ่มเป้าหมาย และตัวชี้วัด

### วัตถุประสงค์

1. จัดทำแหล่งข้อมูลท่องเที่ยวและวัฒนธรรมที่มีผู้รับผิดชอบและรอบตรวจสอบข้อมูล
2. เปิดให้ผู้ประกอบการรับจองบริการ ขายสินค้า และติดตามรายการจนส่งมอบได้
3. ให้ชุมชนใช้เครื่องมือเผยแพร่และประเมินผลการโปรโมทด้วยตนเอง
4. จัดระบบความน่าเชื่อถือ การช่วยเหลือ และธุรกรรมที่ตรวจสอบได้
5. เตรียมสถาปัตยกรรมรองรับการขยายจำนวนชุมชน รายการ และผู้ใช้งาน โดยมีแผนทดสอบก่อนขยาย

### กลุ่มเป้าหมาย

กลุ่มผู้ใช้หลักคือนักท่องเที่ยวในประเทศไทย ผู้ซื้อสินค้าท้องถิ่น ผู้ประกอบการ ช่างฝีมือ ผู้จัดกิจกรรม และผู้ประสานงานชุมชน ภาษาไทยเป็นภาษาตั้งต้น พร้อมเตรียมโครงสร้างภาษาอังกฤษ การเลือกเน้นนักท่องเที่ยวไทยหรือต่างชาติต้องยืนยันในช่วงสำรวจ

กลุ่มร่วมดำเนินงาน ได้แก่ ผู้ดูแลเนื้อหา ฝ่ายบริการลูกค้า ฝ่ายการเงิน และหน่วยงานพันธมิตรที่เกี่ยวข้อง การเป็นพันธมิตรหรือได้รับการรับรองจากหน่วยงานใดยังไม่ถือว่าเกิดขึ้นจนมีข้อตกลงจริง

## 3 ขอบเขตระบบและผู้ใช้งาน

เวอร์ชันเต็มระยะแรกประกอบด้วยส่วนสาธารณะ พื้นที่ลูกค้า พื้นที่ผู้ประกอบการ พื้นที่ชุมชน และระบบผู้ดูแล โดยใช้บัญชีร่วมกันแต่ควบคุมสิทธิ์ตามบทบาทและร้านที่สังกัด

| ส่วนงาน          | ความสามารถหลัก                                                     |
| ---------------- | ------------------------------------------------------------------ |
| ชุมชนและวัฒนธรรม | เรื่องราว สถานที่ พิกัด เทศกาล มารยาท เครดิตและสิทธิ์เผยแพร่       |
| ค้นหาและแผนที่   | จังหวัด ความสนใจ งบ วันที่ จำนวนคน ระยะทาง และสิ่งอำนวยความสะดวก   |
| บริการ           | รอบกิจกรรม ไกด์ เวิร์กช็อป ที่พักหรือรถรับส่งเมื่อมีแบบข้อมูลเฉพาะ |
| การจอง           | จองทันทีหรือรอรับคำขอ ยืนยัน ชำระ เช็กอิน เลื่อน ยกเลิกและคืนเงิน  |
| สินค้า           | ตัวเลือก สต็อก พรีออร์เดอร์ หลายร้าน จัดส่ง รับเอง คืนสินค้า       |
| โปรโมท           | หน้าร้าน ลิงก์และ QR บทความ แคมเปญ คูปอง สถิติ และโฆษณาที่ติดป้าย  |
| ลูกค้าสัมพันธ์   | แชต แจ้งเตือน รีวิว ติดตามร้าน รายการโปรด แผนทริปและช่วยเหลือ      |
| การเงิน          | ชำระ จัดสรรยอด ค่าธรรมเนียม คืนเงิน รายรับ โอนและกระทบยอด          |
| บริหาร           | ตรวจร้านและเนื้อหา จัดสิทธิ์ ข้อร้องเรียน รายงานและประวัติแก้ไข    |

### ขอบเขตสิทธิ์

ลูกค้าเห็นเฉพาะรายการของตน ร้านเห็นเฉพาะลูกค้าและรายการที่จำเป็นต่อการส่งมอบ ผู้ประสานงานช่วยลงข้อมูลได้เมื่อร้านมอบสิทธิ์ ฝ่ายเนื้อหาไม่มีสิทธิ์โอนเงิน ส่วนฝ่ายการเงินเข้าถึงเฉพาะข้อมูลที่จำเป็น การตรวจสิทธิ์ต้องทำที่ Backend ทุกครั้ง แม้หน้าจอจะซ่อนเมนูไว้แล้ว

### ขอบเขตต่อยอด

AI แนะนำทริป ระบบสมาชิกสะสมสิทธิ์ พาร์ตเนอร์รับผลตอบแทน แพ็กเกจรวมหลายผู้ให้บริการ และแอปมือถือแบบติดตั้ง เป็นงานต่อยอดตามผลใช้งาน การโพสต์โซเชียลอัตโนมัติต้องตรวจสิทธิ์ API ก่อนรับเป็นข้อผูกพัน

ระบบไม่ได้รวมการสร้างเครือข่ายขนส่งของตนเอง การออกสินเชื่อ กระเป๋าเงินที่ผู้ใช้เก็บมูลค่า หรือระบบบัญชีตามกฎหมายครบชุด การเพิ่มงานเหล่านี้ต้องกำหนดโครงการย่อยและข้อกำหนดเฉพาะ

## 4 รูปแบบบริการและกระบวนการธุรกิจ

### เส้นทางนักท่องเที่ยว

ค้นพบชุมชน → ดูกิจกรรมและเงื่อนไข → เลือกรอบและจำนวน → ระบบกันที่ว่างชั่วคราว → ชำระหรือรอผู้จัดรับตามรูปแบบ → ได้ใบยืนยัน → รับการแจ้งเตือน → เช็กอิน → รีวิว การชำระสำเร็จยึดผลที่ตรวจสอบจากผู้ให้บริการชำระเงิน ไม่ยึดเพียงหน้าจอที่ลูกค้ากลับมา

### เส้นทางซื้อสินค้า

เลือกสินค้าหลายร้าน → ตรวจสต็อกและค่าจัดส่ง → สร้างคำสั่งซื้อแยกร้าน → ชำระตามรูปแบบที่ผู้ให้บริการรองรับ → ร้านเตรียมและจัดส่ง → ติดตาม → ส่งมอบ → รีวิว หากร้านหนึ่งยกเลิก ต้องคืนเฉพาะยอดที่จัดสรรให้ร้านนั้นได้

### เส้นทางผู้ประกอบการ

สมัครและส่งข้อมูล → ตรวจสอบ → สร้างร้านและรายการ → เปิดขาย → รับงาน → ส่งมอบ → ติดตามยอดสุทธิและรอบโอน ผู้ขายต้องเห็นค่าธรรมเนียม ภาระส่วนลด และเงื่อนไขคืนเงินก่อนเริ่มขาย

### การช่วยเหลือและการเงิน

ทุกข้อร้องเรียนผูกกับรายการและหลักฐาน ตั้งผู้รับผิดชอบ กำหนดเวลาตอบและทางส่งต่อ การคืนเงินมีสถานะขอคืน อนุมัติ กำลังดำเนินการ และสำเร็จ การโอนรายรับมีบัญชีรายการแยกจากคำสั่งซื้อ เพื่อแก้ไขและกระทบยอดโดยไม่เขียนทับประวัติเดิม

### รูปแบบรายได้ที่เสนอ

รายได้หลักอาจมาจากค่าธรรมเนียมรายการสำเร็จ ส่วนรายได้เสริมอาจเป็นแพ็กเกจเครื่องมือร้าน พื้นที่โปรโมทที่ระบุว่าเป็นโฆษณา และบริการกิจกรรมสำหรับองค์กร อัตราค่าธรรมเนียมยังไม่กำหนด ควรสำรวจความสามารถจ่ายและต้นทุนบริการลูกค้าก่อน

ห้ามใช้ยอดรับชำระทั้งหมดเป็นรายได้แพลตฟอร์มในการวิเคราะห์ รายได้แพลตฟอร์มต้องแยกจากเงินที่ต้องชำระให้ผู้ขาย เงินคืน ค่าใช้จ่ายชำระเงิน และภาษีที่เกี่ยวข้อง

## 5 สถาปัตยกรรมระบบที่เสนอ

ใช้ Modular Monolith คือ Backend ชุดเดียวที่แบ่งโมดูลธุรกิจและผู้รับผิดชอบข้อมูลชัดเจน ร่วมกับ Worker สำหรับงานเบื้องหลัง สามารถเพิ่มจำนวนเครื่อง API และ Worker แยกกันได้ การแยกเป็น Microservices จะพิจารณาเมื่อมีปัญหาโหลดหรือขอบเขตทีมที่วัดได้

```text
ลูกค้า  ผู้ขาย  ชุมชน  เจ้าหน้าที่
                ↓
         CDN และ WAF
                ↓
      Next.js Web และ Admin
                ↓
     Load Balancer → NestJS API
                ├→ PostgreSQL และ PostGIS
                ├→ Redis สำหรับแคช
                └→ Outbox ในฐานข้อมูล
                          ↓
                     SQS → Workers
                          ├→ แจ้งเตือนและไฟล์
                          ├→ เชื่อมชำระและขนส่ง
                          └→ Search และ Analytics

รูปและวิดีโอ → Object Storage → CDN
ข้อมูลรายงาน → พื้นที่วิเคราะห์แยกจากฐานธุรกรรม
```

PostgreSQL เป็นแหล่งข้อมูลหลักของรายการและการเงิน Redis และดัชนีค้นหาสามารถสร้างใหม่จากข้อมูลหลักได้ รูปและวิดีโอเก็บใน Object Storage โดยฐานข้อมูลเก็บเพียงข้อมูลอ้างอิงและสิทธิ์เข้าถึง

Outbox คือบันทึกเหตุการณ์ในธุรกรรมเดียวกับการเปลี่ยนข้อมูล แล้วให้ Worker ส่งต่อภายหลัง ลดช่องว่างที่บันทึกคำสั่งซื้อแล้วแต่ยังส่งงานแจ้งเตือนไม่สำเร็จ ผู้รับเหตุการณ์ต้องรองรับการได้รับซ้ำ

API ต้องไม่ฝากสถานะสำคัญไว้เฉพาะหน่วยความจำเครื่องใดเครื่องหนึ่ง เพื่อให้เพิ่มเครื่องและเปลี่ยนเครื่องได้ งานแปลงภาพ รายงาน และ AI ไม่ทำในคำขอจองหรือชำระเงินโดยตรง

PWA ใช้บันทึกหน้าและใบจองที่อนุญาตให้ดูแบบออฟไลน์ได้ แต่การตรวจที่ว่าง ชำระ และยืนยันเช็กอินต้องมีการซิงก์กับระบบ ไม่แสดงผลสำเร็จจากข้อมูลออฟไลน์โดยไม่มีหลักฐาน

MapLibre เป็นตัวแสดงแผนที่ ไม่ได้รวมข้อมูลแผนที่ การค้นหาที่อยู่ หรือคำนวณเส้นทางฟรีโดยอัตโนมัติ ต้องเลือกบริการและงบแต่ละส่วน แอป React Native พิจารณาภายหลังเมื่อมีเหตุผล เช่น การใช้งานซ้ำสูงหรือความสามารถเครื่องที่เว็บทำได้ไม่เพียงพอ

## 7 เทคโนโลยี Backend และการเชื่อมต่อ

NestJS รองรับ TypeScript และมีแนวทางแบ่งโครงสร้างแอป [S02] ใช้โมดูล Identity, Community, Catalog, Booking, Commerce, Payments, Payouts, Promotion, Messaging และ Support โดยแต่ละโมดูลมีขอบเขตข้อมูลและบริการชัดเจน

กำหนด API เช่น /v1/bookings, /v1/orders และ /v1/refunds ตรวจสิทธิ์ระดับรายการทุกครั้ง ใช้รหัสคำขอและ Idempotency Key สำหรับการสร้างธุรกรรมซ้ำ พร้อมกำหนดอายุการเก็บคีย์ รูปแบบข้อผิดพลาด และข้อจำกัดจำนวนคำขอ

แยก Adapter ของ Payment, Shipping, Maps และ Notifications ออกจากกฎธุรกิจ ระบบจึงเปลี่ยนผู้ให้บริการได้โดยทดสอบสัญญาข้อมูลเดิม การรองรับ LINE Login การแบ่งเงินร้าน และคืนเงินบางส่วนต้องทดลองกับผู้ให้บริการที่เลือก ไม่ถือว่า Managed OIDC หรือ Payment Gateway ทุกรายทำได้เหมือนกัน

ในพื้นที่ทำงานมีการประกาศใช้ Next.js, React, NestJS, Node.js และ pg อยู่แล้ว ข้อมูลนี้ยืนยันเพียงการเลือกแพ็กเกจ ไม่ใช่ผลตรวจความพร้อมระบบเดิม ต้องสำรวจโค้ด การทดสอบ และโครงสร้างข้อมูลก่อนใช้ซ้ำ ล็อกรุ่นที่เข้ากันได้เมื่อเริ่มพัฒนาและทบทวนแพตช์สม่ำเสมอ [S14]

## 8 โครงสร้างฐานข้อมูลและความสัมพันธ์

ใช้ฐานข้อมูลเชิงสัมพันธ์เป็นหลัก เพราะคำสั่งซื้อ การจอง สต็อก และเงินมีข้อจำกัดที่ต้องรักษาพร้อมกัน กำหนด Foreign Key, Unique และ Check Constraint ตามกฎธุรกิจ ไม่พึ่งการตรวจในหน้าจอเพียงอย่างเดียว

| กลุ่มข้อมูล     | ตารางหลักที่เสนอ                           | ความสัมพันธ์สำคัญ                        |
| --------------- | ------------------------------------------ | ---------------------------------------- |
| ผู้ใช้และสิทธิ์ | users, identities, roles, memberships      | ผู้ใช้หนึ่งคนมีสมาชิกหลายร้านได้         |
| ชุมชน           | communities, places, stories, translations | ชุมชนมีสถานที่และเนื้อหาหลายรายการ       |
| ร้าน            | merchants, merchant_communities, staff     | ร้านเชื่อมหลายชุมชนได้โดยตารางกลาง       |
| สินค้า          | products, variants, stock_movements        | สินค้าหนึ่งรายการมีหลายตัวเลือก          |
| บริการ          | services, schedules, inventory_holds       | บริการมีรอบและการถือที่ว่างหลายรายการ    |
| จอง             | bookings, participants, booking_events     | การจองอ้างรอบและมีประวัติสถานะ           |
| ซื้อ            | checkouts, orders, order_items             | Checkout หนึ่งชุดมี Order แยกร้าน        |
| เงิน            | payments, allocations, refunds             | การชำระจัดสรรไปหลายรายการได้             |
| บัญชีภายใน      | journal_entries, journal_lines, payouts    | บันทึกยอดและการกลับรายการแบบตรวจย้อนหลัง |
| ส่งมอบ          | shipments, pickup_events, returns          | Order มีการส่งและคืนหลายครั้งได้         |
| เนื้อหาอื่น     | reviews, campaigns, tickets, messages      | ผูกสิทธิ์กับผู้ใช้และรายการที่เกี่ยวข้อง |
| ระบบ            | outbox_events, webhook_events, audit_logs  | คีย์เหตุการณ์ป้องกันประมวลผลซ้ำ          |

ใช้ UUID สำหรับตัวระบุหลักหรือแนวทางที่ทีมกำหนดสม่ำเสมอ รหัสที่เดายากไม่ทดแทนการตรวจสิทธิ์ เก็บจำนวนเงินเป็นจำนวนเต็มหน่วยย่อย เช่น สตางค์ พร้อมรหัสสกุลเงิน ไม่ใช้ floating point

เก็บเวลาที่เป็นเหตุการณ์ด้วย timestamptz และแสดงเป็น Asia/Bangkok เก็บวันเวลาเปิดบริการและเขตเวลาที่เกี่ยวข้องแยกเมื่อจำเป็น ใช้ JSONB สำหรับข้อมูลเสริมและ snapshot เงื่อนไข ไม่ใช้แทนคอลัมน์หลักที่ต้องเชื่อมและตรวจความถูกต้อง

เก็บพิกัดแบบ geography Point พร้อม SRID 4326 และดัชนี GiST สำหรับงานระยะทางตามแบบสอบถามที่ทดสอบ PostGIS มีฟังก์ชันค้นหาเชิงพื้นที่ที่ใช้ดัชนีได้ [S05] เอกสารยืนยันตัวตนและไฟล์ส่วนบุคคลอยู่ในพื้นที่ไฟล์ส่วนตัว ไม่ใส่ URL สาธารณะในหน้าร้าน

## 9 ความถูกต้องของสต็อก การจอง และการเงิน

### ป้องกันขายเกิน

เมื่อถือสินค้า/ที่ว่าง ให้ใช้ธุรกรรมสั้นและ row lock หรือ conditional update ที่ตรวจจำนวนคงเหลือในคำสั่งเดียว บันทึก hold พร้อมเวลาหมดอายุใน PostgreSQL เมื่อต้องแก้หลายแถวให้ล็อกตามลำดับคงที่และมี bounded retry เมื่อเกิด deadlock แนวทาง locking อ้างอิงความสามารถ PostgreSQL [S06]

Redis ช่วยให้หน้าค้นหาเร็ว แต่ไม่เป็นแหล่งตัดสินว่าขายสิทธิ์สุดท้ายได้หรือไม่ การปลด hold และการยืนยันต้องเป็น atomic operation เพื่อไม่ให้ Worker ปลดที่ว่างพร้อมกับการชำระสำเร็จ

### ป้องกันรายการซ้ำ

กำหนด unique key ของเหตุการณ์ชำระและ idempotency request ตรวจลายเซ็น webhook และบันทึกรับเหตุการณ์ก่อนประมวลผล ไม่เรียกบริการภายนอกค้างไว้ระหว่างถือ database lock การส่งคำขอคืนเงินหรือโอนเงินซ้ำต้องใช้รหัสอ้างอิงเดิมและตรวจผลเดิมก่อน

### สมุดรายการเงินภายใน

ออกแบบ journal แบบรายการเพิ่มต่อเนื่อง โดยยอดเดบิตและเครดิตต่อรายการต้องสมดุลตามสกุลเงิน การแก้ยอดใช้รายการกลับหรือปรับปรุงที่อ้างเหตุผล ห้ามแก้ตัวเลขเก่าทิ้งเฉย ๆ ระบบนี้เป็นบัญชีควบคุมธุรกรรมภายใน ต้องให้ผู้รับผิดชอบบัญชีตรวจการเชื่อมกับบัญชีและภาษีจริง

กระทบยอดทุกวันระหว่างยอดชำระ ยอดคืน ค่าบริการภายนอก ยอดจัดสรรผู้ขาย และการโอนจริง แยกรายการผิดปกติให้เจ้าหน้าที่จัดการ รอบโอนควรอิงเงื่อนไขส่งมอบและข้อพิพาทที่ตกลงกับผู้ให้บริการชำระเงิน ไม่ออกแบบการถือเงินแทนผู้ขายโดยไม่มีโมเดลบริการรองรับ

### เมื่อเหตุการณ์มาช้าหรือผิดลำดับ

เงินมาหลัง hold หมดอายุให้ตรวจสต็อกอีกครั้ง ถ้าไม่พอให้เข้าคิวคืนหรือช่วยเหลือ เหตุการณ์เก่าไม่ทำให้สถานะย้อนจากสำเร็จเป็นรอชำระ เก็บหลักฐานเหตุการณ์ทั้งหมดและใช้กฎเปลี่ยนสถานะที่ทดสอบได้

## 10 แผนฐานข้อมูลขนาดใหญ่และการขยายระบบ

จำนวนสมาชิกไม่เท่ากับภาระฐานข้อมูล ต้องวัดคำขอต่อวินาที อัตราเขียนพร้อมกัน ขนาดข้อมูลจริง แบบสอบถาม และช่วงพีก ก่อนสรุปว่าจะรองรับผู้ใช้ได้กี่คน

### ลำดับการขยาย

1. ออกแบบดัชนีตามคำค้นจริง เช่น orders(merchant_id, created_at, id) และ bookings(schedule_id, status) ตรวจ EXPLAIN ANALYZE ในสภาพแวดล้อมปลอดภัย พร้อมดู slow queries และ autovacuum
2. ใช้ cursor pagination สำหรับรายการยาว จำกัดจำนวนแถว และแก้ปัญหาเรียกข้อมูลซ้ำแบบ N+1 เพิ่ม connection pool ที่คำนวณรวมทุก API และ Worker ไม่เกินงบ connection ของฐานข้อมูล
3. เพิ่มขนาดเครื่องและ I/O ตามคอขวด แคชเฉพาะข้อมูลที่ยอมล่าช้าได้ และแยกภาพออกผ่าน CDN
4. เพิ่ม read replica สำหรับข้อมูลอ่านที่ยอมล่าช้า เช่น รายงานบางชนิด งานตรวจที่ว่าง ชำระ และข้อมูลหลังแก้ไขใหม่ให้อ่าน primary เพราะ replica อาจตามไม่ทัน [S04]
5. แบ่งตารางเหตุการณ์และประวัติขนาดใหญ่ตามเดือนเมื่อการลบข้อมูลเก่าหรือแบบสอบถามได้รับประโยชน์จริง PostgreSQL partitioning มีข้อจำกัดเรื่องคีย์และการออกแบบที่ต้องตรวจ [S03]
6. ย้ายงานวิเคราะห์หนักไปคลังข้อมูล แยกบริการหรือ shard เฉพาะเมื่อ primary ยังติดคอขวดหลังปรับแล้ว และมีแผนความสอดคล้องข้ามส่วน

### จุดตัดสินใจที่เสนอ

| สัญญาณต่อเนื่องในช่วงโหลดที่ออกแบบ          | การตรวจและแนวทาง                                     |
| ------------------------------------------- | ---------------------------------------------------- |
| API p95 เกินเป้าหมาย                        | ดู trace ว่าช้าที่ฐานข้อมูล ภายนอก หรือประมวลผล      |
| DB CPU หรือ I/O สูงกว่า 70% เป็นช่วงยาว     | ตรวจคำค้น ดัชนี ล็อก และขนาดเครื่องก่อนเพิ่ม replica |
| พื้นที่ว่างต่ำกว่า 30% หรือคาดเต็มใน 30 วัน | เพิ่มความจุ ตรวจ retention และการโตของดัชนี          |
| คิวงานเก่ากว่าเป้าหมาย                      | เพิ่ม Worker และตรวจบริการปลายทางก่อนเพิ่มอัตรา      |
| คำค้นภาษาไทยไม่ตรงความตั้งใจ                | ทดลองดัชนีค้นหาและวัดคุณภาพด้วยชุดคำค้นจริง          |
| รายงานกระทบการซื้อหรือจอง                   | แยกข้อมูลวิเคราะห์และตรวจความสดของรายงาน             |

ไม่แบ่งฐานข้อมูลตามจังหวัดตั้งแต่ต้น เพราะลูกค้าและคำสั่งซื้ออาจเกี่ยวข้องหลายพื้นที่ การ shard ต้องเลือกคีย์จากภาระจริงและออกแบบย้ายข้อมูล การค้นข้าม shard และการกระทบยอดก่อน

## 11 แบบจำลองโหลดและพื้นที่จัดเก็บ

ตารางนี้เป็นเป้าหมายทดสอบสามระดับ ไม่ใช่ผล benchmark หรือคำรับรองของเทคโนโลยี ต้องทดสอบซ้ำกับสเปกและชุดข้อมูลที่เลือกจริงก่อนขยายแต่ละระดับ

| ตัวแปร                        | ทดลอง  | เติบโต  | ขยายมาก   |
| ----------------------------- | ------ | ------- | --------- |
| สมาชิกสะสม                    | 10,000 | 100,000 | 1,000,000 |
| ผู้ใช้ต่อวัน                  | 1,000  | 10,000  | 100,000   |
| ผู้ใช้กำลังใช้งานช่วงพีก      | 100    | 1,000   | 10,000    |
| คำขอ API ต่อวินาที            | 20     | 200     | 2,000     |
| คำสั่งเปลี่ยนธุรกรรมต่อวินาที | 2      | 20      | 200       |
| รายการซื้อและจองเฉลี่ยต่อวัน  | 100    | 1,000   | 10,000    |

สมมติผู้ใช้ที่กำลังใช้งานส่ง API เฉลี่ยหนึ่งครั้งต่อ 5 วินาที จึงได้ 100 ÷ 5 = 20 requests/second คำสั่งเปลี่ยนธุรกรรมเป็นส่วนหนึ่งของคำขอทั้งหมดและหนึ่งรายการอาจมีหลายคำสั่ง ไม่ใช่จำนวนการชำระสำเร็จต่อวินาที หน้าแคชและไฟล์จาก CDN ไม่รวมในตัวเลขนี้

### ตัวอย่างพื้นที่เมื่อมี 10,000 รายการต่อวัน

สมมติข้อมูลรวมต่อรายการ 12 KB และดัชนีเพิ่ม 100% จะใช้ประมาณ 10,000 × 365 × 12 KB × 2 = 87.6 GB ต่อปี หากมี audit 20 เหตุการณ์ต่อรายการ เหตุการณ์ละ 1 KB จะเพิ่ม 73 GB ต่อปี รวมประมาณ 160.6 GB ก่อนเผื่อการขยายตัวของดัชนี ประวัติอื่น WAL replica และ backup จึงใช้ 250 GB เป็นฐานทดสอบต่อปีของตัวอย่างนี้ ไม่ใช่ขนาดซื้อจริง

สำหรับสื่อ หากมีรูป 100,000 รูป รูปละ 2 MB จะมีต้นฉบับ 200 GB หากรูปย่อยเพิ่ม 50% จะรวม 300 GB ตัวเลขนี้แยกจากฐานข้อมูล และยังไม่รวมวิดีโอ การเปิดดูซ้ำส่งผลต่อค่า bandwidth แม้ขนาดเก็บไม่เพิ่ม

### วิธีทดสอบ

ใช้ k6 สร้างข้อมูลและโหลดแบบใกล้จริง อ่าน 90% เปลี่ยนข้อมูล 10% รวมคำค้นไทย คำสั่งซื้อหลายร้าน และการแย่งสิทธิ์สุดท้าย ทำ baseline 60 นาที spike 3 เท่าเป็นเวลา 10 นาที และ soak test 8 ชั่วโมง ตรวจ latency, error, connection, lock, queue age และต้นทุน หลังทดสอบต้องกระทบยอดรายการ ไม่ดูเฉพาะความเร็ว

## 12 ระบบค้นหา ข้อมูลวิเคราะห์ และ AI

### การค้นหา

ช่วงแรกใช้ PostgreSQL สำหรับตัวกรองและพิกัด พร้อมทดสอบข้อความไทยจากข้อมูลจริง หากคุณภาพค้นหาหรือโหลดไม่ผ่านเกณฑ์ ให้ใช้ OpenSearch เป็นดัชนีเฉพาะ มี Thai analyzer ตามเอกสาร [S09] แต่ต้องทดสอบชื่อท้องถิ่น คำสะกดหลายแบบ และคำพ้อง ไม่สรุปว่าการเปิด analyzer ทำให้ผลค้นหาดีครบทุกกรณี

อัปเดตดัชนีด้วยเหตุการณ์จาก Outbox กำหนดเป้าหมายข้อมูลตามทัน เช่น ภายใน 60 วินาที และมีงานเทียบข้อมูลกับฐานหลัก รายการที่หยุดขายต้องถูกตรวจอีกครั้งก่อนจองแม้ยังพบในผลค้นหา

### งานเบื้องหลัง

ใช้ SQS แยกคิวแจ้งเตือน ไฟล์ รายงาน และงานเชื่อมต่อ กำหนด timeout, retry แบบหน่วงเวลา, จำนวนครั้ง และ Dead Letter Queue สำหรับงานที่ล้มเหลวต่อเนื่อง Standard queue ส่งซ้ำได้ จึงต้องทำ consumer ให้ประมวลผลซ้ำแล้วไม่สร้างผลซ้ำ [S08]

### การวิเคราะห์

เริ่มจากรายงานสรุปที่คำนวณตามรอบ แยกจากเส้นทางชำระ เมื่อปริมาณมาก ใช้การส่งออกเพิ่มเฉพาะส่วนเปลี่ยนแปลงหรือ CDC ไป Object Storage แบบ Parquet แล้ววิเคราะห์ด้วย Athena และแสดงผ่าน Metabase ตามความเหมาะสม ตรวจสิทธิ์เชื่อมต่อและค่า query ก่อนเลือกจริง

กำหนดนิยาม event เช่น view_item, begin_checkout, payment_confirmed และ service_completed ให้สอดคล้องกัน พร้อมรหัสอ้างอิงสำหรับตัดรายการซ้ำ ลดข้อมูลส่วนบุคคลและกำหนดระยะเก็บตั้งแต่ต้น

### AI ระยะต่อยอด

ใช้ข้อมูลชุมชนที่อนุมัติแล้วในการช่วยค้นหาและร่างแผนทริป แสดงแหล่งอ้างอิงและเวลาข้อมูล ตรวจราคาและที่ว่างผ่าน API จริงก่อนให้ผู้ใช้ยืนยัน AI ไม่เปลี่ยนยอด โอนเงิน หรือยืนยันการจองเองจากข้อความที่สร้างขึ้น การใช้ vector search เช่น pgvector ต้องทดลองคุณภาพและโหลดก่อนติดตั้งเป็นส่วนหลัก

## 13 Cloud ความปลอดภัย และการกู้คืน

### ชุดโครงสร้างพื้นฐานอ้างอิง

เสนอ AWS เป็นตัวอย่างสำหรับประเมินราคา: CloudFront และ WAF ด้านหน้า, ECS Fargate สำหรับ Web/API/Worker, RDS PostgreSQL แบบ Multi-AZ สำหรับธุรกรรม, S3 สำหรับไฟล์, SQS สำหรับคิว และ Redis แบบจัดการให้เมื่อจำเป็น ใช้ Infrastructure as Code เช่น Terraform เก็บการตั้งค่าที่ทบทวนและสร้างซ้ำได้ Fargate เป็นทางเลือกสำหรับรัน container โดยไม่ต้องจัดการเซิร์ฟเวอร์ underlying เอง [S11]

เลือก region หลังตรวจความหน่วง ข้อกำหนดข้อมูล บริการที่มี และราคา API และฐานข้อมูลควรอยู่ใกล้กัน แยก development, staging และ production พร้อมบัญชีและสิทธิ์ที่เหมาะสม ไม่ใช้ข้อมูลส่วนบุคคลจริงในระบบพัฒนา

Multi-AZ แบบหนึ่ง standby เน้นความพร้อมและ failover โดย standby ไม่รับงานอ่าน ต้องแยกจาก read replica [S07] หาก production ตั้งเป้าความพร้อมสูง ควรมี API มากกว่าหนึ่ง instance กระจาย Availability Zone ส่วนจำนวนและสเปกต้องผ่านทดสอบโหลด

### มาตรการความปลอดภัย

- ใช้ TLS, private network สำหรับฐานข้อมูล, Secrets Manager และสิทธิ์น้อยที่สุด
- ตรวจ authentication และ authorization ระดับร้านและรายการ พร้อม MFA ของเจ้าหน้าที่
- ใช้ session cookie แบบ Secure, HttpOnly และการป้องกัน CSRF ที่เหมาะกับรูปแบบใช้งาน
- จำกัดคำขอ ตรวจไฟล์อัปโหลด สแกนไฟล์ที่จำเป็น และใช้ signed URL กับข้อมูลส่วนตัว
- ปกปิดข้อมูลส่วนบุคคลและ secret ใน log ตรวจ dependency และช่องโหว่ก่อน release
- ให้ผู้ให้บริการชำระเงินจัดการข้อมูลบัตรผ่านหน้าที่เหมาะสม ไม่เก็บข้อมูลบัตรเต็มเอง

### Backup และ Disaster Recovery

เปิด automated backup และ PITR ซึ่งอาศัยฐานสำรองและบันทึกการเปลี่ยนแปลง [S12] เสนอ RPO ไม่เกิน 15 นาที และ RTO ไม่เกิน 4 ชั่วโมงเป็นเป้าหมายตั้งต้นสำหรับเหตุเสียหายที่กำหนด ไม่ใช่ SLA ที่รับรองแล้ว กำหนดการเก็บ backup เช่น 35 วันหลังตรวจงบและนโยบาย สำเนากู้ภัยข้ามพื้นที่พิจารณาตามความเสี่ยงและข้อกำหนดข้อมูล

ทดสอบกู้คืนก่อนเปิดและทุกไตรมาส รวมฐานข้อมูล ไฟล์ key/config และการกระทบยอดภายนอก Replica ไม่ทดแทน backup เพราะความเสียหายเชิงตรรกะอาจถูกส่งต่อไปด้วย

### งานที่ทำคู่ขนานได้

ระหว่างพัฒนาระบบ ให้ทีมชุมชนจัดทำข้อมูลและขอสิทธิ์สื่อ ทีมธุรกิจเลือกผู้ให้บริการชำระและขนส่ง ทีมออกแบบทดสอบหน้าจอล่วงหน้าหนึ่งรอบ และ QA เตรียมกรณีทดสอบตั้งแต่ระยะแรก ไม่รอให้พัฒนาเสร็จทั้งหมด

### เส้นทางที่ส่งผลต่อกำหนดเปิด

นโยบายธุรกรรม → อนุมัติผู้ให้บริการชำระ → เชื่อมและทดสอบ → กระทบยอดและคืนเงิน → ทดลองจริง หากส่วนนี้ล่าช้า ให้เลื่อนการรับเงินจริง แต่ยังทดสอบเนื้อหาและร้านในสภาพแวดล้อมจำลองต่อได้

AI แอปมือถือ และแพ็กเกจหลายผู้ให้บริการอยู่หลังสัปดาห์ที่ 40 และต้องประเมินแยก ส่วนที่พักหรือรถรับส่งหากต้องเปิดพร้อม pilot ต้องย้ายงานเฉพาะเข้าระยะ 13 ถึง 24 และประเมินคนหรือเวลาเพิ่ม

## 16 งบประมาณและต้นทุนการดำเนินงาน

งบต่อไปนี้เป็นแบบจำลองจากสมมติฐานกำลังคน ไม่ใช่ราคาตลาด ใบเสนอราคา หรือราคาผู้ให้บริการ Cloud ใช้เพื่อคุยกรอบลงทุนก่อนขอราคาอย่างน้อยตามขอบเขตเดียวกัน

### ตัวอย่างการคิดงบพัฒนา

สมมติ 40 สัปดาห์เท่ากับ 10 เดือนงบประมาณ กำลังเฉลี่ย 7 คน รวม 70 person-month หากใช้อัตราต้นทุนรวมสมมติ 70,000 ถึง 120,000 บาทต่อคนต่อเดือน จะได้งบทีม 4.90 ถึง 8.40 ล้านบาท

| หมวด                                            | วิธีประมาณ                     | ช่วงตัวอย่าง           |
| ----------------------------------------------- | ------------------------------ | ---------------------- |
| ทีมพัฒนาและบริหาร                               | 70 person-month × อัตราสมมติ   | 4.90 ถึง 8.40 ล้านบาท  |
| สำรวจ เนื้อหา อบรม ตรวจเฉพาะทางและระบบช่วงพัฒนา | เงินเผื่อแยกเพื่อขอราคาจริง    | 0.50 ถึง 1.20 ล้านบาท  |
| รวมก่อนเงินเผื่อ                                | ผลรวมสองรายการ                 | 5.40 ถึง 9.60 ล้านบาท  |
| เงินเผื่อความเสี่ยง                             | 20% ของยอดก่อนเงินเผื่อ        | 1.08 ถึง 1.92 ล้านบาท  |
| กรอบรวมตัวอย่าง                                 | ก่อนภาษีและค่าใช้จ่ายที่ไม่รวม | 6.48 ถึง 11.52 ล้านบาท |

อัตราสมมติไม่ได้ยืนยันว่าจะจัดหาทีมได้ในราคานี้ และช่วงคนทำงานจริงอาจไม่เท่ากัน หากมีระบบเดิมใช้ซ้ำได้ ต้องหักงานหลังตรวจแล้วเท่านั้น ไม่คำนวณลดงบจากจำนวนแพ็กเกจที่มีอยู่

### งบรายเดือนหลังเปิด

จัดทำ Bill of Materials แยก API/Web/Worker, ฐาน primary และ standby, read replica หากใช้, cache, search, storage, backup, CDN/egress, NAT/network, monitoring และ staging จากนั้นใส่ราคาตาม region และปริมาณใช้งานจริง

แยกค่าใช้จ่ายตามรายการ ได้แก่ ค่าชำระเงิน ข้อความ แผนที่ ขนส่ง AI และคืนเงิน ออกจากค่า Cloud คงที่ ตัวอย่างเงินตั้งสำรอง Cloud และเครื่องมือใน pilot 30,000 ถึง 100,000 บาทต่อเดือนใช้ได้เพียงเป็นกรอบขอราคา ต้องปรับเมื่อมี BOM ไม่ใช่ข้อรับรองว่าระบบตามแบบจะอยู่ในช่วงนี้

งบนี้ยังไม่รวมทีมบริการลูกค้าประจำหลังเปิด งบซื้อโฆษณา ค่าขนส่งที่แพลตฟอร์มอุดหนุน แอป native และโมดูลต่อยอด ให้เจ้าของโครงการกำหนดค่าเหล่านี้แยก พร้อมติดตามต้นทุนต่อรายการสำเร็จและต่อชุมชนที่ใช้งานจริง

## 17 การทดสอบและเกณฑ์คุณภาพ

ตั้งเป้าระบบหลักพร้อมใช้งาน 99.9% ต่อเดือนเป็น SLO ภายในที่เสนอ ซึ่งเท่ากับเวลาที่ไม่พร้อมได้ประมาณ 43.2 นาทีในเดือน 30 วัน ต้องกำหนดขอบเขตการวัดและผลจากบริการภายนอกก่อนใช้เป็นสัญญา

| ด้าน         | เป้าหมายตั้งต้น                                             | หลักฐาน                                              |
| ------------ | ----------------------------------------------------------- | ---------------------------------------------------- |
| ความเร็ว API | อ่าน p95 ไม่เกิน 500 ms และเปลี่ยนข้อมูลไม่เกิน 1 วินาที    | Load test ที่ระดับเป้าหมาย ไม่รวมเวลารอผู้ใช้/ภายนอก |
| หน้าจอ       | เนื้อหาหลักปรากฏภายใน 3 วินาทีตามอุปกรณ์และเครือข่ายที่ตกลง | Browser test และข้อมูลผู้ใช้จริง                     |
| ความถูกต้อง  | ไม่ซ้ำ ไม่ขายเกิน และยอดเงินตรง                             | Concurrent test และ reconciliation                   |
| ความปลอดภัย  | ไม่มีช่องโหว่ร้ายแรงค้างก่อนเปิด                            | รายงานตรวจและหลักฐานแก้                              |
| การกู้คืน    | RPO และ RTO ผ่านเป้าหมายในสถานการณ์ที่ตกลง                  | บันทึกซ้อมกู้คืน                                     |
| การเข้าถึง   | ตรวจเส้นทางหลักตามเกณฑ์ที่กำหนด                             | Automated และ manual accessibility test              |

ใช้ unit test กับกฎราคา สต็อก และสถานะ; integration test กับ PostgreSQL จริงในระบบทดสอบ; contract test กับผู้ให้บริการ; Playwright กับเส้นทางผู้ใช้; k6 กับโหลด; และ security review ก่อนเปิด

กรณีบังคับคือกดชำระซ้ำ เงินมาช้า webhook ผิดลำดับ hold หมดอายุ จองสิทธิ์สุดท้ายพร้อมกัน คืนเงินบางร้าน ไฟล์อัปโหลดผิดประเภท ร้านเข้าถึงข้อมูลร้านอื่น และระบบภายนอกหยุดตอบ

ติดตาม logs, metrics และ traces ผ่าน OpenTelemetry เพื่อเชื่อมเหตุขัดข้องข้ามส่วน [S10] ตั้ง alert ตามผลกระทบ เช่น ชำระค้าง กระทบยอดไม่ตรง queue age และ error rate กำหนดผู้รับแจ้งและคู่มือแก้ก่อนเปิด alert จริง

### ข้อมูลและข้อกำหนดธุรกิจ

จัดทำทะเบียนข้อมูล วัตถุประสงค์ ผู้เข้าถึง ระยะเก็บ และวิธีใช้สิทธิของเจ้าของข้อมูล แยกการส่งข่าวการตลาดออกจากข้อความธุรกรรม ให้ผู้รับผิดชอบตรวจฐานการประมวลผลและข้อกำหนดที่ใช้กับธุรกิจจริง ไม่ใช้ความยินยอมแบบเดียวกับข้อมูลทุกประเภทโดยอัตโนมัติ

ต้องตรวจหน้าที่ตามกฎหมายบริการแพลตฟอร์มดิจิทัลตามลักษณะและขนาดของบริการ ETDA มีคำอธิบายผู้ประกอบการที่เข้าข่ายและการแจ้ง [S13] ส่วนใบอนุญาตกิจกรรม ที่พัก การนำเที่ยว สินค้า และรูปแบบรับเงิน ให้ตรวจตามบริการที่จะเปิดจริงก่อนเปิดประเภทนั้น เอกสารนี้ไม่ตัดสินสถานะทางกฎหมายแทนการตรวจเฉพาะธุรกิจ

### เกณฑ์ส่งมอบโครงการ

ส่งมอบ source code, ประวัติการพัฒนา, ERD และ data dictionary, OpenAPI, migrations, โครงสร้าง Cloud, คู่มือ deploy/rollback, รายงานทดสอบ, คู่มือผู้ขายและผู้ดูแล, การสำรองและกู้คืน และบัญชีบริการภายนอกที่เจ้าของโครงการควบคุมได้

ตรวจรับเมื่อเส้นทางจองและซื้อครบถึงส่งมอบ/คืนเงิน สิทธิ์แยกผู้ใช้ถูกต้อง ยอดกระทบได้ โหลดตามข้อตกลงผ่าน ซ้อมกู้คืนสำเร็จ ไม่มีปัญหาวิกฤตค้าง และมีผู้รับผิดชอบ production จริง ระยะรับประกันและเวลาตอบเหตุให้ระบุในสัญญาจัดจ้างแยก

วัน 1 ถึง 2 ยืนยันชื่อ พื้นที่ ประเภทบริการ งบ และเจ้าของการตัดสินใจ วัน 3 ถึง 5 สัมภาษณ์ผู้ใช้และสำรวจระบบเดิม วัน 6 ถึง 8 จัดทำต้นแบบสามเส้นทางและ ERD รุ่นแรก วัน 9 ถึง 10 ทดลองต้นแบบ ทบทวนนโยบายเงิน และแบ่ง backlog พร้อมประเมิน effort รอบแรก
