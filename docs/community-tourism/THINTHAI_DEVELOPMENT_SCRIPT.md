# ThinThai Development Script

วันที่ 4 ตุลาคม 2569

เอกสารนี้เป็น Script หรือบรีฟสำหรับสั่งทีมพัฒนาหรือ AI Coding Agent ให้พัฒนา ThinThai ตามลำดับ ไม่ใช่โปรแกรมติดตั้งหรือระบบที่สร้างเสร็จแล้ว ใช้ร่วมกับ PROJECT_PROPOSAL.md และ PRODUCT_SCOPE.md ในโฟลเดอร์เดียวกัน โดยชื่อแบรนด์และเงื่อนไขที่ระบุในเอกสารนี้เป็นทิศทางล่าสุด

## 1 ข้อความแบรนด์ที่ยืนยันแล้ว

- ชื่อแอป: ThinThai
- คำโปรยหลัก: แอปเดียวครบ จองทริป ช้อปสินค้าชุมชน
- คำอธิบายแบรนด์: เที่ยวไทยให้ถึงถิ่น สัมผัสวิถีชีวิต วัฒนธรรมและธรรมชาติอันงดงาม
- ใช้ตัวพิมพ์ ThinThai ให้ตรงกันในหน้าเว็บ ชื่อแอป และเอกสาร
- ยังไม่มีโลโก้หรือโดเมนที่ยืนยัน ห้ามอ้างว่าจดทะเบียนหรือได้รับการรับรองแล้ว
- ข้อเสนอคำแปลภาษาอังกฤษที่ยังต้องตรวจทาน: One app for local trips and community shopping.

## 2 Master Script สำหรับสั่งพัฒนา

คุณคือทีมพัฒนาผลิตภัณฑ์ ThinThai ทำหน้าที่วิเคราะห์ระบบ ออกแบบ UX/UI พัฒนา Frontend และ Backend ออกแบบฐานข้อมูล ทดสอบ และเตรียมระบบสำหรับการดูแลจริง

สร้างแพลตฟอร์มตัวกลางท่องเที่ยว วัฒนธรรม บริการ สินค้าชุมชน และอาหารในประเทศไทย โดยให้ชุมชนและผู้ประกอบการจัดการข้อมูลของตนเอง ลูกค้าค้นหา จอง ซื้อ และติดตามรายการได้ และมีผู้ดูแลตามพื้นที่พร้อมผู้ดูแลส่วนกลาง

ก่อนแก้โค้ด ให้สำรวจโครงการปัจจุบัน อ่าน AGENTS.md ที่เกี่ยวข้อง ตรวจแพ็กเกจ migration สิทธิ์ และการทดสอบที่มีอยู่ รายงานว่าส่วนใดใช้ซ้ำได้ ต้องปรับ หรือขาด ห้ามสรุปว่าระบบพร้อมจากการเห็นชื่อแพ็กเกจเพียงอย่างเดียว เก็บงานเดิมของผู้ใช้และไม่สร้างระบบซ้ำโดยไม่จำเป็น

ใช้ชื่อและข้อความแบรนด์ตามบทที่ 1 สร้างงานเป็นช่วงที่ตรวจสอบได้ แยกข้อมูลจำลอง การเชื่อมต่อ sandbox และ production ชัดเจน ห้ามแสดงการชำระเงินหรือจองจริงว่าสำเร็จโดยไม่มีหลักฐานจากระบบ

## 3 ประสบการณ์ใช้งานและอุปกรณ์

สร้าง Responsive Web App พร้อมโครงสร้าง PWA ใช้ได้จากเบราว์เซอร์บนมือถือ แท็บเล็ต และคอมพิวเตอร์ ออกแบบตามความกว้างพื้นที่จริง รวมการหมุนหน้าจอและ split screen ไม่ใช้ชื่ออุปกรณ์เป็นเงื่อนไขหลักในการจัดหน้า

- มือถือ: หน้าแบบคอลัมน์เดียว การ์ดแทนตาราง เมนูล่าง และปุ่มหลักที่กดสะดวก
- แท็บเล็ต: รายการคู่รายละเอียด หรือแผนที่คู่ข้อมูล เมื่อมีพื้นที่เพียงพอ
- คอมพิวเตอร์: เมนูด้านข้าง ตัวกรอง ตาราง และรายละเอียดพร้อมกัน
- เป้าหมายออกแบบตั้งต้น: เนื้อหาประมาณ 18 px และเป้าสัมผัสประมาณ 48 × 48 px ทดสอบข้อความขยายและคีย์บอร์ดด้วย
- ไอคอนต้องมีข้อความหรือชื่อที่เทคโนโลยีช่วยอ่านเข้าถึงได้ ไม่ใช้สีบอกสถานะอย่างเดียว
- ต้องมีสถานะโหลด ไม่มีข้อมูล ผิดพลาด สิทธิ์ไม่พอ ออฟไลน์ และลองใหม่
- รายการในแท็บต้องตรงหมวด เช่น แท็บอาหารไม่แสดงการจองกิจกรรม
- ข้อมูลออฟไลน์ดูได้เฉพาะที่อนุญาต การชำระ ตรวจสต็อก และยืนยันการจองต้องตรวจระบบออนไลน์

ใช้สีเขียวอมฟ้า #00695C เป็นสีหลัก พื้นครีม #FFF9F1 พื้นการ์ดขาว และข้อความเข้ม #173832 สีส้มใช้เน้นข้อมูลหรือการติดตาม ตรวจ contrast ตามตำแหน่งจริงก่อนยืนยันแบบ

## 4 หน้าแรกและข้อความสั้น

หน้าแรกใช้โลโก้ข้อความ ThinThai ตามด้วยคำโปรยหลักและคำอธิบายแบรนด์ที่ผู้ใช้ให้ ช่องค้นหาใช้ “อยากไปที่ไหน?” เมนูหลักใช้ “เที่ยว” “กิจกรรม” “ที่พัก” “ของฝาก” และ “อาหาร” โดยจัดให้เหมาะกับพื้นที่จอ

จัดเนื้อหาเป็น ชุมชนน่าเที่ยว กิจกรรมแนะนำ ของดีชุมชน และอาหารใกล้คุณ ส่วนอาหารใกล้คุณต้องมีจุดส่งที่ลูกค้าเลือก ไม่บังคับขอตำแหน่งก่อนอ่านเนื้อหาทั่วไป

ใช้ปุ่ม “ค้นหา” “เลือกวัน” “ดูรายละเอียด” “เพิ่มลงตะกร้า” “ตรวจรายการ” “ชำระเงิน” และ “ติดตาม” ตามงานจริง หลีกเลี่ยงปุ่มคลุมเครือ เช่น “ตกลง” ในขั้นที่มีการเรียกเก็บเงิน

ข้อมูลตัวอย่างต้องติดป้าย ไม่สร้างรีวิว ยอดผู้ใช้ เครื่องหมายรับรอง หรือราคาโปรโมทแล้วแสดงเสมือนเป็นข้อมูลจริง

## 5 บทบาทและสิทธิ์

| บทบาท       | สิทธิ์                                                 | ขอบเขต                               |
| ----------- | ------------------------------------------------------ | ------------------------------------ |
| User        | ค้นหา จอง ซื้อ สั่งอาหาร แชต รีวิว ขอช่วยเหลือ         | รายการและข้อมูลของตน                 |
| Merchant    | จัดการร้าน สินค้า บริการ รอบ ออเดอร์ และรายรับ         | ร้านที่มีสมาชิกและสิทธิ์             |
| Admin       | ตรวจร้านและเนื้อหา ดูแลงาน พื้นที่อาหารและข้อร้องเรียน | พื้นที่และความสามารถที่ได้รับมอบหมาย |
| Super Admin | มอบสิทธิ์ ตั้งค่าส่วนกลาง เปิดโมดูล และตรวจประวัติ     | ทั้งระบบตามสิทธิ์งานที่กำหนด         |

หนึ่งบัญชีมีหลายบทบาทได้ แต่ไม่สามารถเลือกเลื่อนสิทธิ์ให้ตนเองจากหน้าจอได้ ตรวจ authorization ที่ API และขอบเขตข้อมูลทุกครั้ง แยกสิทธิ์อ่าน แก้ไข อนุมัติ และงานการเงิน การดูแลทั้งระบบไม่ใช่เหตุให้แสดงข้อมูลส่วนบุคคลทั้งหมดโดยไม่จำเป็น

กำหนด Admin scope ด้วยพื้นที่และชนิดงาน งานข้ามพื้นที่ต้องมีเจ้าของงานชัดเจน ไม่เปิดข้อมูลให้ Admin ทุกพื้นที่โดยอัตโนมัติ ผู้ประสานงานชุมชนและคนส่งสามารถเพิ่มเป็นบทบาทเฉพาะภายหลังผ่านระบบสิทธิ์เดียวกัน โดยไม่ใช้สิทธิ์ Admin แทน

## 6 กฎอาหารและพื้นที่ที่ต้องรักษา

การจำกัดโซนบริการใช้เฉพาะอาหารพร้อมทานแบบส่งทันที ท่องเที่ยว กิจกรรม ที่พัก และสินค้าทั่วไปเปิดใช้งานตามกฎของโมดูลนั้น ไม่ถูกปิดด้วยโซนอาหาร

แยกหมวดสินค้าออกจากวิธีส่งมอบ กำหนดประเภท instant_food_delivery, parcel_delivery, pickup และ service_booking แต่ละรายการรองรับวิธีที่ระบุได้ ไม่อนุมานจากคำว่าอาหารอย่างเดียว

- อาหารส่งทันที: ตรวจปลายทาง โซน เวลาเปิดร้าน ความพร้อม และเงื่อนไขส่ง
- อาหารแห้งหรือของฝาก: ใช้ข้อกำหนดพัสดุและข้อจำกัดสินค้านั้น
- รับเอง: จุดรับและเวลารับที่ร้านรองรับ
- บริการ: รอบ ความจุ จำนวนคน และวันว่าง

เก็บจังหวัด อำเภอ ตำบลเป็นข้อมูลอ้างอิงที่มีรหัสและความสัมพันธ์ ใช้คำว่าเขตและแขวงเมื่อเป็นกรุงเทพมหานคร บันทึกแหล่งที่มาและวันที่ข้อมูลขอบเขต

เก็บ delivery_zones แยกจากเขตการปกครอง เป็น polygon หรือ multipolygon พร้อม version วันเริ่มใช้ เวลาให้บริการ และพื้นที่ยกเว้น โซนหนึ่งข้ามตำบลได้ ร้านหนึ่งเชื่อมหลายโซนได้

หน้า Admin “พื้นที่และจัดส่งอาหาร” ต้องมีตัวกรองจังหวัด อำเภอ ตำบล แผนที่ หมุดร้าน จุดรับ จุดส่ง และเครื่องมือทดสอบปลายทาง ตรวจ polygon ที่ไม่ถูกต้อง โซนทับกัน หมุดบนเส้นขอบ และพื้นที่งดส่ง กำหนดกฎลำดับความสำคัญให้ชัด

การปิดโซนมีผลกับการรับงานใหม่ตามเวลาที่กำหนด ต้องแจ้งผลกระทบต่องานค้าง ไม่ลบประวัติหรือยกเลิกงานเก่าโดยเงียบ ๆ บันทึกโซนและกติกาค่าส่งฉบับที่ใช้กับออเดอร์

## 7 ชุดเทคโนโลยีและโครงสร้าง

ใช้ Next.js, React และ TypeScript สำหรับเว็บ ใช้ NestJS บน Node.js รุ่น LTS ที่ยังรองรับสำหรับ Backend ใช้ PostgreSQL กับ PostGIS เป็นแหล่งข้อมูลธุรกรรมและพิกัด ตรวจรุ่นที่เข้ากันได้และแพตช์ปัจจุบันก่อนติดตั้ง

ใช้ Tailwind CSS และชุดองค์ประกอบที่เข้าถึงได้สำหรับ UI, next-intl สำหรับภาษา, pg และ SQL migrations สำหรับฐานข้อมูลตามฐานโครงการเดิม ใช้ OpenAPI เป็นสัญญา REST API ไม่แชร์ entity ฐานข้อมูลที่มีข้อมูลลับออกไปยัง Frontend

โครงสร้างเป้าหมายที่ปรับเข้ากับโครงการเดิมได้:

```text
apps/
  web/                 ลูกค้าและผู้ประกอบการ
  admin/               Admin และ Super Admin
  api/                 กฎธุรกิจและ API
  worker/              งานเบื้องหลัง
packages/
  ui/                  องค์ประกอบหน้าจอร่วม
  contracts/           รูปแบบ API และ client ที่สร้างจาก OpenAPI
  i18n/                คำแปลและการตั้งค่าภาษา
  config/              กติกาพัฒนาและตรวจคุณภาพ
database/
  migrations/          ประวัติเปลี่ยนโครงสร้าง
  seeds/               ข้อมูลจำลองสำหรับพัฒนา
infra/                 การตั้งค่าโครงสร้างพื้นฐาน
tests/                 การทดสอบข้ามโมดูลและระบบ
docs/                  ข้อกำหนด สถาปัตยกรรมและคู่มือ
```

เริ่ม Backend แบบ Modular Monolith และแยก Worker เพิ่มเครื่อง API กับ Worker แยกกันได้ Redis เป็นแคชเมื่อจำเป็น ไม่เป็นฐานตัดสินยอดเงินหรือสิทธิ์สุดท้าย เก็บไฟล์ใน Object Storage ใช้ Queue สำหรับแจ้งเตือนและงานใช้เวลานาน โดยเลือกผู้ให้บริการให้สอดคล้อง Cloud ที่อนุมัติ

## 8 โมดูลและข้อมูลหลัก

โมดูลหลักคือ Identity, Communities, Content, Merchants, Catalog, Booking, Commerce, FoodDelivery, Payments, Payouts, Promotion, Support และ Audit

ข้อมูลหลักประกอบด้วย users, memberships, roles, permissions, admin_scopes, communities, administrative_areas, merchants, products, variants, fulfillment_options, services, schedules, holds, bookings, checkouts, orders, order_items, delivery_zones, zone_versions, delivery_jobs, payments, allocations, refunds, payouts, journal_entries, journal_lines, outbox_events และ audit_logs

ออกแบบ ERD และ data dictionary ก่อนเขียน migration ระบุ PK, FK, unique constraint และดัชนีจากรูปแบบค้นจริง ใช้จำนวนเต็มหน่วยย่อยสำหรับเงินพร้อม currency เก็บเวลาเหตุการณ์ด้วย timestamptz ใช้ JSONB กับข้อมูลเสริมหรือ snapshot ไม่แทนคอลัมน์หลักที่ต้องตรวจความสัมพันธ์

แยกสถานะ order, payment, fulfillment และ refund เพื่อไม่ให้สถานะส่งอาหารกลบสถานะเงิน บันทึกราคา เงื่อนไข คูปอง และการจัดสรรยอด ณ เวลายืนยัน

## 9 ความถูกต้องของธุรกรรม

ใช้ transaction สั้น row lock หรือ conditional update สำหรับสต็อกและความจุ การถือและปลด hold ต้องป้องกันการแข่งกัน ระบุเวลาหมดอายุและกรณีเงินเข้าหลังหมดเวลา

รองรับ Idempotency Key ใน API สำคัญ ตรวจลายเซ็น webhook และ unique event ID เหตุการณ์ซ้ำต้องไม่สร้างคำสั่งซื้อ คืนเงิน หรือโอนเงินซ้ำ ใช้ Outbox ส่งงานหลังบันทึกข้อมูล และทำ consumer ให้รับเหตุการณ์ซ้ำได้โดยไม่มีผลซ้ำ

สินค้าทั่วไปมี checkout หลายร้านแล้วแยก order ตามร้าน อาหารส่งทันทีเริ่มหนึ่งร้านต่อ order และแยก checkout จากพัสดุ การจองกิจกรรมใช้ขั้นตอนเฉพาะ ห้ามรวมการชำระหลายร้านก่อนตรวจว่าผู้ให้บริการและโมเดลธุรกิจรองรับ

สร้างบัญชีควบคุมยอดภายในที่แก้ด้วยรายการกลับ ไม่เขียนทับรายการเก่า และกระทบยอดชำระ คืนเงิน ค่าธรรมเนียมกับยอดผู้ขายได้

## 10 ภาษาและความเป็นสากล

ลำดับภาษา: ภาษาที่ผู้ใช้เลือกในครั้งนั้นหรือ URL ที่ระบุภาษา → ภาษาที่บันทึกไว้ → ภาษาที่เบราว์เซอร์แจ้งและระบบรองรับ → ภาษาอังกฤษเป็น fallback เตรียมภาษาไทยและอังกฤษก่อน ภาษาอื่นเพิ่มผ่านชุดคำแปล

ใช้ Accept-Language และ navigator.languages ไม่ใช้ AI เดาภาษาของเครื่อง เปลี่ยนภาษาแล้วต้องคงหน้า ตะกร้า และรายการเดิม มีปุ่มเลือกภาษาที่เข้าถึงได้ ไม่ใช้ธงประเทศเป็นตัวแทนภาษาเพียงอย่างเดียว

AI ช่วยแปลเนื้อหาและค้นหาได้ในอนาคต คำแปลราคา เงื่อนไข และความปลอดภัยต้องตรวจทาน สกุลเงินและเขตเวลาแยกจากภาษา แสดง THB และเวลาบริการไทยให้ชัดเมื่อเกี่ยวข้อง

## 11 การขยายและการดูแล

เริ่มจากดัชนี connection pool cursor pagination และวัด slow queries ก่อนเพิ่มเครื่อง แยกไฟล์ผ่าน CDN เพิ่ม read replica สำหรับงานอ่านที่ยอมล่าช้าได้ งานยืนยันเงินและที่ว่างอ่านข้อมูลหลัก

เพิ่มระบบค้นหาเฉพาะเมื่อคุณภาพค้นไทยหรือโหลดไม่ผ่าน แบ่งตารางเหตุการณ์ตามช่วงเวลาเมื่อมีเหตุผลด้านคำค้นและ retention แยกรายงานหนักจากฐานธุรกรรม ไม่ shard ตามจังหวัดเพียงเพราะมีหลายจังหวัด

ใช้ feature flag เปิดความสามารถตามกลุ่มร้านหรือพื้นที่ได้ แต่ flag ไม่ทดแทน authorization แยก Adapter ผู้ให้บริการเงิน แผนที่ ขนส่ง และ AI เตรียม version API สำหรับแอปอื่นในอนาคต

แยก development, staging และ production ใช้ secret management และสิทธิ์น้อยที่สุด ไม่ฝัง key ในหน้าเว็บหรือ repo เก็บ log โดยปกปิดข้อมูลส่วนบุคคล พร้อม backup และซ้อมกู้คืนจริง

## 12 ลำดับสั่งพัฒนา

### ช่วง A สำรวจและวางฐาน

ตรวจระบบเดิม สรุปส่วนใช้ซ้ำ จัดทำ ERD ตารางสิทธิ์ เส้นทางหน้าจอ และข้อเสนอการตั้งชื่อ ThinThai ในโค้ดโดยไม่เปลี่ยน identifier ที่มีผลต่อระบบเดิมแบบเงียบ ๆ จัดทำ backlog และเกณฑ์ตรวจรับรายช่วง

### ช่วง B โครงแอปและบัญชี

สร้างโครงหน้าจอทั้ง 4 บทบาท ภาษาไทยและอังกฤษ ระบบสมาชิกและสิทธิ์ร่วม พร้อมการทดสอบเข้าถึงข้อมูลข้ามผู้ใช้และข้ามร้าน เตรียมหน้ามือถือ แท็บเล็ตและคอมพิวเตอร์ด้วยข้อมูลจำลองติดป้าย

### ช่วง C ชุมชนและรายการ

สร้างร้าน สินค้า บริการ ชุมชนและเนื้อหา พร้อมคิวตรวจ เผยแพร่ พิกัด และการค้นหา ใช้ข้อมูลตัวอย่างที่ไม่แสดงเสมือนเป็นร้านจริง

### ช่วง D ซื้อและจอง

พัฒนาสต็อก รอบ hold checkout booking payment sandbox การส่งมอบ ยกเลิก คืน และรายรับ ทดสอบรายการซ้ำและผู้ใช้พร้อมกันก่อนขยาย

### ช่วง E จัดส่งอาหาร

พัฒนาจังหวัด อำเภอ ตำบล โซนอาหาร หมุด ทดสอบจุดส่ง ค่าส่ง และมอบหมายคนส่ง คงฟังก์ชันอื่นเปิดตามปกติ ทดสอบร้านขายหลายรูปแบบส่งมอบ

### ช่วง F ทดสอบและเปิดนำร่อง

ทดสอบความปลอดภัย accessibility โหลด การกระทบยอดและกู้คืน อบรมผู้ดูแลและร้าน กำหนดผู้รับผิดชอบปัญหาและเงื่อนไขเปิดเงินจริงกับเจ้าของโครงการ

### ช่วง G ต่อยอด

เพิ่มแคมเปญ แผนทริป ระบบค้นหาเฉพาะ AI และแอป native ตามผลใช้งานและการประเมินใหม่ ไม่ถือว่าทุกส่วนพร้อมเพียงเพราะมีเมนูในภาพตัวอย่าง

## 13 เกณฑ์ตรวจรับสำคัญ

- ชื่อ ThinThai และข้อความแบรนด์ตรงกับที่กำหนด
- User และ Merchant ดูข้อมูลของผู้อื่นนอกสิทธิ์ไม่ได้ แม้เรียก API โดยตรง
- Admin ทำงานได้เฉพาะพื้นที่และความสามารถที่มอบหมาย
- การเปลี่ยนบทบาท โซน ราคา และค่าธรรมเนียมมีประวัติ
- หมุดนอกโซนทำให้อาหารส่งทันทีใช้ไม่ได้ แต่ยังจองกิจกรรมและซื้อสินค้าทั่วไปได้ตามกฎของรายการ
- อาหารแพ็กส่งพัสดุไม่ถูกจำกัดด้วยโซนส่งอาหารโดยผิดพลาด
- โซนทับกัน เส้นขอบ พื้นที่งดส่ง และบริการแผนที่ขัดข้องมีผลลัพธ์ชัดเจน
- การจองหรือซื้อสิทธิ์สุดท้ายพร้อมกันไม่ทำให้ขายเกิน
- กดซ้ำหรือรับ webhook ซ้ำไม่ทำให้ยอดและรายการซ้ำ
- เปลี่ยนภาษาและหมุนจอไม่ทำข้อมูลที่กรอกหาย
- หน้าจอสำคัญใช้งานได้ที่ความกว้าง 360, 768, 1024 และ 1440 px พร้อมทดสอบ zoom และอุปกรณ์จริงที่ตกลง
- ขั้นชำระ การคืนเงิน และรายรับกระทบยอดกันได้
- สำรองและกู้คืนผ่านตามเป้าหมายที่ตกลงก่อนเปิด

## 14 รูปแบบรายงานจากผู้พัฒนา

เมื่อจบแต่ละช่วง ให้รายงานสิ่งที่ทำได้จริง ส่วนที่ยังเป็น mock/sandbox ไฟล์หรือหน้าที่เปลี่ยน วิธีทดสอบและผล ข้อจำกัดที่ยังมี และงานช่วงถัดไป ห้ามกล่าวว่ารองรับทุกอุปกรณ์หรือผู้ใช้จำนวนหนึ่งโดยไม่มีผลทดสอบ

กรณียังไม่มีผู้ให้บริการภายนอกหรือข้อมูลธุรกิจที่จำเป็น ให้ทำส่วนที่ไม่ขึ้นต่อข้อมูลนั้นต่อได้ พร้อมระบุรายการตัดสินใจ ไม่สร้าง credential นโยบายราคา หรือการอนุมัติแทนเจ้าของโครงการ

## 15 คำสั่งเริ่มงานแบบสั้น

พัฒนา ThinThai ตาม THINTHAI_DEVELOPMENT_SCRIPT.md โดยเริ่มช่วง A สำรวจโครงการเดิมและวางฐานก่อน ใช้ PROJECT_PROPOSAL.md และ PRODUCT_SCOPE.md ประกอบ รักษางานเดิมและสิทธิ์ผู้ใช้ แสดงแผนไฟล์ โครงข้อมูล ตารางสิทธิ์ และผลตรวจส่วนที่ใช้ซ้ำได้ จากนั้นดำเนินงานช่วงที่ได้รับมอบหมายพร้อมทดสอบตามเกณฑ์ ห้ามเปิดรับเงินจริงหรือย้ายข้อมูล production โดยอาศัยบรีฟนี้เพียงอย่างเดียว
