# แพลตฟอร์มท่องเที่ยว วัฒนธรรม และตลาดชุมชน

เอกสารขอบเขตระบบและแผนหน้าจอ ฉบับ 0.1 — 4 ตุลาคม 2026

สถานะ: ข้อเสนอสำหรับทบทวนและประเมินงานพัฒนา ยังไม่ใช่นโยบายที่อนุมัติหรือระบบที่เปิดใช้งานจริง

เอกสารนี้อิงบทสนทนาเรื่องแพลตฟอร์มท่องเที่ยวชุมชนครั้งนี้ ไม่แทนที่แผนโครงการอื่นในพื้นที่ทำงาน ชื่อแบรนด์และความสัมพันธ์กับโครงการเดิมยังรอยืนยัน

## 1. เป้าหมายและขอบเขต

เชื่อมโยงนักท่องเที่ยวกับชุมชนไทย ให้คนในพื้นที่เล่าเรื่องวัฒนธรรม โปรโมทบริการ รับจองกิจกรรม และขายผลิตภัณฑ์ พร้อมดูแลลูกค้าจนจบรายการ

เส้นทางหลัก: ค้นพบชุมชน → อ่านเรื่องราว → เลือกกิจกรรมหรือสินค้า → จองหรือซื้อ → รับบริการหรือสินค้า → รีวิว → กลับมาใช้ซ้ำ

### สิ่งที่ผู้ใช้ระบุแล้ว

- ให้บริการในประเทศไทย เน้นแหล่งท่องเที่ยว วัฒนธรรม และท้องถิ่น
- เป็นแพลตฟอร์มตัวกลาง มีบริการ สินค้า และช่องทางโปรโมท
- ต้องการภาพเต็มของระบบและฟีเจอร์ที่ครบถ้วน
- ขั้นตอนนี้จัดทำขอบเขต ผังหน้าจอ และขั้นตอนใช้งานเพื่อเตรียมพัฒนา

### สมมติฐานเพื่อให้แบบเดินหน้าต่อได้

- เริ่มจากเว็บที่ใช้สะดวกบนมือถือ รองรับภาษาไทยและโครงสร้างหลายภาษา
- ออกแบบรองรับหลายชุมชน แต่ทดลองเปิดจริงในพื้นที่จำกัดก่อน
- บุคคลหนึ่งเป็นทั้งลูกค้าและผู้ขายได้ โดยสลับบทบาท
- เชื่อมผู้ให้บริการชำระเงินและขนส่งภายนอก ชื่อผู้ให้บริการยังไม่เลือก
- ตะกร้าสินค้ารวมหลายร้านได้ แต่แยกคำสั่งซื้อ ค่าส่ง และเงินคืนตามร้าน
- การจองบริการแยกจากตะกร้าสินค้า; แพ็กเกจรวมหลายผู้ให้บริการเป็นงานระยะต่อยอด
- เรื่องราว ราคา จำนวนที่ว่าง และข้ออ้างด้านผลกระทบชุมชนต้องมีแหล่งข้อมูลหรือเจ้าของข้อมูล

## 5. โครงหน้าจอสำคัญสำหรับออกแบบต่อ

### หน้าชุมชน

1. ภาพหลัก ชื่อชุมชน จังหวัด และคำแนะนำสั้น
2. ปุ่มดูแผนที่ บันทึก และแชร์
3. เรื่องราวจากคนในพื้นที่พร้อมเครดิต
4. กิจกรรมที่จองได้ / สินค้า / ร้านค้า / เทศกาล
5. การเดินทาง สิ่งอำนวยความสะดวก กติกาชุมชน และวันที่ตรวจสอบข้อมูล

### หน้ารายละเอียดกิจกรรม

1. รูป ชื่อ ผู้จัด สถานะยืนยัน และรีวิว
2. ราคาเริ่มต้น พร้อมเงื่อนไขราคา; เลือกวันและจำนวนคนเพื่อแสดงราคาจริง
3. ระยะเวลา ภาษา ความเหมาะสม และการเข้าถึง
4. ตารางกิจกรรม สิ่งที่รวม/ไม่รวม จุดนัดพบ และสิ่งที่ต้องเตรียม
5. เงื่อนไขยกเลิก สภาพอากาศ และจำนวนผู้เข้าร่วมขั้นต่ำ
6. ปุ่มเลือกรอบและตรวจราคาก่อนชำระ

### หน้าตรวจรายการก่อนชำระ

1. รายการ วันเวลา/ที่อยู่ และผู้ขาย
2. ยอดสินค้า/บริการ ส่วนลด ค่าส่ง ค่าธรรมเนียม และยอดรวม
3. เงื่อนไขยกเลิกหรือคืนสินค้าที่เกี่ยวข้อง
4. ช่องทางชำระ และกรอบเวลาที่ถือสิทธิ์รายการไว้
5. ปุ่มยืนยันแสดงยอดชัดเจน; ป้องกันการกดซ้ำ

### หน้างานวันนี้ของผู้ขาย

1. งานต้องทำก่อน: คำขอใกล้หมดเวลา สินค้ารอส่ง กิจกรรมใกล้เริ่ม
2. งานวันนี้แยกตามสถานะและเวลา
3. ปุ่มรับงาน เตรียมส่ง เช็กอิน และติดต่อผู้ซื้อ
4. สรุปรายรับแยกเงินที่รอดำเนินการกับเงินที่โอนแล้ว

ทุกหน้าต้องออกแบบสถานะไม่มีข้อมูล กำลังโหลด ล้มเหลว สิทธิ์ไม่พอ และข้อมูลเปลี่ยนระหว่างใช้งานด้วย

## 6. ขั้นตอนใช้งานหลัก

### 6.1 สมัครเป็นผู้ให้บริการ

สมัครบัญชี → เลือกประเภทร้านและชุมชน → กรอกข้อมูลและส่งเอกสารที่จำเป็น → เจ้าหน้าที่ตรวจ → อนุมัติหรือขอข้อมูลเพิ่ม → สร้างรายการ → ตรวจเผยแพร่ตามนโยบาย → เริ่มรับงาน

การเปลี่ยนข้อมูลรับเงินต้องยืนยันเพิ่มเติม แจ้งเจ้าของบัญชี และมีประวัติการเปลี่ยนแปลง

### 6.2 ลูกค้าจองกิจกรรมแบบยืนยันทันที

เลือกกิจกรรม → เลือกวัน/รอบ/จำนวน → ตรวจที่ว่างและราคา → ถือที่ว่างชั่วคราว → ชำระเงิน → ระบบรับผลยืนยันจากผู้ให้บริการชำระเงิน → ยืนยันการจอง → แจ้งทั้งสองฝ่าย → เช็กอิน → จบกิจกรรม → รีวิวและดำเนินการรายรับตามนโยบาย

การกลับมาที่หน้าชำระสำเร็จเพียงอย่างเดียวไม่ถือเป็นหลักฐานว่าได้รับเงินแล้ว

### 6.3 ลูกค้าจองแบบรอผู้จัดยืนยัน

ส่งคำขอ → กันความจุตามคำขอชั่วคราว → ผู้จัดตอบภายในเวลาที่กำหนด → หากรับ จึงเปิดให้ชำระภายในเวลาที่กำหนด → ชำระสำเร็จจึงยืนยัน → หากปฏิเสธ/หมดเวลา ปลดความจุ

ข้อเสนอตั้งต้นคือไม่ตัดเงินก่อนผู้จัดรับคำขอ ค่าระยะเวลาถือที่ว่างและเวลาตอบรับยังต้องกำหนด

### 6.4 ลูกค้าซื้อสินค้า

เลือกสินค้า → ตะกร้า → เลือกจัดส่งหรือรับเอง → ตรวจสต็อกและราคา → แยกคำสั่งซื้อตามร้าน → ชำระ → ร้านเตรียมสินค้า → แจ้งส่งและเลขติดตาม/รหัสรับสินค้า → ส่งมอบ → รีวิว

หากจ่ายรวมหลายร้าน ต้องมีรายการชำระหลักและยอดจัดสรรให้แต่ละคำสั่งซื้อ เพื่อคืนเงินเฉพาะร้านที่มีปัญหาได้

### 6.5 ชุมชนเผยแพร่เรื่องราวและโปรโมท

สมาชิกหรือผู้ประสานงานร่าง → ระบุเจ้าของภาพ/เนื้อหาและการอนุญาต → ผู้มีสิทธิ์ตรวจ → เผยแพร่ → เชื่อมกิจกรรมและสินค้า → แชร์ลิงก์ → ดูสถิติ → ทบทวนข้อมูลตามรอบ

### 6.6 ยกเลิกและคืนเงิน

ลูกค้าส่งคำขอพร้อมเหตุผล → ระบบแสดงสิทธิ์ตามเงื่อนไขที่บันทึกตอนซื้อ → ผู้มีสิทธิ์พิจารณา → คำนวณเงินคืนและผลต่อรายรับ → ส่งคำขอคืนเงิน → ติดตามจนผู้ให้บริการชำระเงินยืนยัน → แจ้งผลทั้งสองฝ่าย

หากมีข้อโต้แย้ง ให้เปิดเรื่องช่วยเหลือที่ผูกหลักฐานและประวัติสนทนา การกดอนุมัติภายในระบบยังไม่เท่ากับเงินคืนถึงลูกค้าแล้ว

## 7. กฎธุรกิจและสถานะ

### กฎหลัก

- บันทึกราคา ค่าธรรมเนียม เงื่อนไข และข้อมูลรายการ ณ เวลายืนยัน เพื่อไม่ให้การแก้หน้าร้านเปลี่ยนรายการเก่า
- ที่ว่างและสต็อกต้องตรวจและจองแบบป้องกันผู้ใช้หลายคนซื้อชิ้นสุดท้ายพร้อมกัน
- คำขอที่หมดเวลาปลดที่ว่าง/สต็อก; หากเงินมาช้า ต้องตรวจความพร้อมอีกครั้งและส่งเข้ากระบวนการแก้ไขหรือคืนเงิน
- ใช้เวลาไทยในการแสดงวันและเวลาบริการ พร้อมระบุเขตเวลาในข้อมูลที่แชร์
- ส่วนลดต้องกำหนดผู้รับภาระ เงื่อนไขซ้อนคูปอง และผลต่อเงินคืน
- สต็อกจะไม่เพิ่มทันทีเพียงเพราะคืนเงิน ต้องยืนยันการคืนของหรือการยกเลิกก่อนจัดส่ง
- รีวิวได้เมื่อรายการผ่านจุดส่งมอบที่กำหนด จำกัดหนึ่งรีวิวต่อรายการที่มีสิทธิ์ และเก็บประวัติแก้ไข
- เครื่องหมายยืนยันบอกขอบเขตการตรวจ ไม่สื่อว่ารับรองคุณภาพทุกด้าน
- การระงับร้านต้องมีแผนจัดการงานค้างและเงินค้าง พร้อมช่องทางอุทธรณ์

### แยกสถานะตามเรื่อง

| เรื่อง     | สถานะหลัก                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------- |
| ร้าน       | ร่าง → รอตรวจ → ต้องแก้ไข/อนุมัติ → เปิดขาย/พัก/ระงับ                                       |
| การจอง     | รอผู้จัด → รอชำระ → ยืนยัน → เช็กอิน → เสร็จสิ้น; ทางแยก: ปฏิเสธ หมดเวลา ยกเลิก ไม่มาตามนัด |
| คำสั่งซื้อ | รอชำระ → รอเตรียม → กำลังเตรียม → ส่งแล้ว/พร้อมรับ → ส่งมอบ; ทางแยก: ยกเลิก ส่งไม่สำเร็จ    |
| เงิน       | รอชำระ → สำเร็จ/ไม่สำเร็จ/หมดเวลา; เงินคืนติดตามเป็นรายการแยก                               |
| คืนสินค้า  | ขอคืน → ตรวจคำขอ → อนุมัติ/ปฏิเสธ → รอรับคืน → ตรวจสินค้า → ปิดเรื่อง                       |
| คืนเงิน    | รอตรวจ → อนุมัติ → กำลังดำเนินการ → สำเร็จ/ล้มเหลว                                          |
| โอนรายรับ  | ยังไม่ถึงรอบ → พร้อมโอน → กำลังโอน → สำเร็จ/ล้มเหลว/พักตรวจ                                 |

สถานะย่อย การเปลี่ยนสถานะ และผู้มีสิทธิ์เปลี่ยนต้องแตกเป็นรายละเอียดก่อนสร้างแต่ละโมดูล

## 8. กรณีผิดปกติที่ต้องรองรับ

| เหตุการณ์                     | พฤติกรรมที่ต้องได้                                                                 |
| ----------------------------- | ---------------------------------------------------------------------------------- |
| ชำระสำเร็จแต่ปิดหน้าเว็บ      | รายการยังยืนยันจากผลชำระฝั่งระบบและเปิดดูย้อนหลังได้                               |
| ได้รับผลชำระซ้ำ               | ไม่สร้างคำสั่งซื้อ/เงินคืน/โอนรายรับซ้ำ                                            |
| ลูกค้าสองคนซื้อสิทธิ์สุดท้าย  | มีผู้ได้สิทธิ์ตามจำนวนจริง อีกคนเห็นข้อความและทางเลือก                             |
| ผู้จัดยกเลิกเพราะสภาพอากาศ    | แจ้งลูกค้าทั้งหมด เสนอเลื่อนหรือคืนตามเงื่อนไข และติดตามรายคน                      |
| ร้านหนึ่งในตะกร้ายกเลิก       | รายการร้านอื่นดำเนินต่อได้ พร้อมคืนเฉพาะส่วนที่เกี่ยวข้อง                          |
| พัสดุสูญหายหรือเสียหาย        | รับหลักฐาน เปิดเรื่อง และติดตามผู้รับผิดชอบจนปิดเรื่อง                             |
| เชื่อมชำระเงินหรือขนส่งไม่ได้ | แสดงสถานะรอตรวจ ไม่เดาว่าสำเร็จ และมีช่องทางเจ้าหน้าที่แก้ไข                       |
| ผู้ขายไม่ตอบรับ               | หมดเวลา แจ้งลูกค้า และคืนความจุอัตโนมัติ                                           |
| แจ้งเตือนส่งไม่สำเร็จ         | รายการยังอยู่ในบัญชี ส่งซ้ำตามขอบเขต และให้เจ้าหน้าที่เห็นงานผิดพลาด               |
| ลูกค้าขอลบบัญชีขณะมีงานค้าง   | อธิบายข้อมูลที่ยังจำเป็นและระยะเก็บตามนโยบาย ไม่ลบหลักฐานรายการแบบขาดความต่อเนื่อง |

## 9. ข้อมูลหลักและการเชื่อมต่อ

ข้อมูลหลัก: บัญชีและบทบาท, ชุมชน, สมาชิกร้าน, สถานที่, เรื่องราวและสิทธิ์เผยแพร่, สินค้าและตัวเลือก, สต็อก, บริการและรอบ, การจอง, คำสั่งซื้อรายร้าน, การจัดส่ง, การชำระ, การจัดสรรยอด, เงินคืน, รายรับ, แคมเปญ, รีวิว, ข้อร้องเรียน และประวัติการแก้ไข

ข้อมูลส่วนบุคคลให้เก็บเฉพาะที่จำเป็นตามวัตถุประสงค์ แยกเอกสารยืนยันตัวตนออกจากข้อมูลสาธารณะ กำหนดผู้เข้าถึง ระยะเก็บ และกระบวนการลบ/ส่งออกก่อนเปิดจริง

| การเชื่อมต่อ       | ข้อมูลหรือความสามารถที่ต้องยืนยันก่อนเลือก                          |
| ------------------ | ------------------------------------------------------------------- |
| ชำระเงิน           | ช่องทางจ่าย คืนบางส่วน แจ้งผลย้อนหลัง กระทบยอด และรูปแบบโอนผู้ขาย   |
| แผนที่             | ค้นหาพิกัด เส้นทาง เงื่อนไขข้อมูล และค่าใช้ตามปริมาณ                |
| ขนส่ง              | พื้นที่บริการ คำนวณค่าส่ง เลขติดตาม และการเคลม                      |
| แจ้งเตือน          | อีเมล/ข้อความ/LINE ตามช่องทางที่ตกลง สิทธิ์เชื่อมต่อ และค่าใช้      |
| วิเคราะห์การใช้งาน | เหตุการณ์ที่ต้องวัด การตั้งค่าความเป็นส่วนตัว และการเก็บข้อมูล      |
| AI ระยะต่อยอด      | แหล่งข้อมูลที่อนุญาต ขอบเขตข้อมูลส่วนบุคคล การตรวจคำตอบ และงบใช้งาน |

ไม่ใส่ข้อสรุปว่าผู้ให้บริการใดรองรับความสามารถเหล่านี้จนกว่าจะตรวจเอกสารและเงื่อนไขจริง

## 10. คุณภาพระบบและเกณฑ์ตรวจรับ

### เป้าหมายคุณภาพที่เสนอ

- ใช้งานหลักผ่านมือถือได้ครบ ไม่ต้องดาวน์โหลดแอปก่อน
- หน้าหลักอ่านและกดใช้งานได้ด้วยคีย์บอร์ด มีข้อความกำกับและคอนทราสต์ที่เหมาะสม
- หน้ารายละเอียดและผลค้นหาต้องทดสอบบนเครือข่ายมือถือ; เป้าหมายเบื้องต้นเนื้อหาหลักปรากฏภายใน 3 วินาทีภายใต้เงื่อนไขทดสอบที่ตกลง
- ระบบธุรกรรมต้องทดสอบผู้ใช้พร้อมกันตามขนาดพื้นที่นำร่องก่อนกำหนดขีดรองรับจริง
- บัญชีเจ้าหน้าที่และการแก้ข้อมูลรับเงินมีการยืนยันเพิ่มเติม
- สำรองและทดสอบกู้คืนข้อมูลก่อนเปิดจริง; เวลากู้คืนและข้อมูลย้อนหลังที่ยอมสูญเสียได้ต้องตกลงกับเจ้าของโครงการ
- มีผู้รับผิดชอบเหตุขัดข้องและช่องทางติดตาม ไม่อ้างบริการช่วยเหลือตลอด 24 ชั่วโมงหากไม่มีทีมรองรับ

## 12. ตัวชี้วัด

- คนดูรายละเอียด → เริ่มจอง/ซื้อ → ชำระสำเร็จ โดยแยกสินค้าและบริการ
- ร้านที่เปิดขายจริงและรายการที่มีข้อมูลพร้อมใช้งาน
- อัตราตอบรับ ระยะเวลาตอบ และอัตรายกเลิกแยกตามสาเหตุ
- รายการส่งมอบสำเร็จ ระยะเวลาคืนเงิน และเรื่องร้องเรียนค้าง
- ยอดขายรวม รายรับผู้ขาย และรายได้แพลตฟอร์มแสดงแยกกัน
- การกลับมาซื้อหรือจองซ้ำตามช่วงเวลาที่กำหนด
- การกระจายรายรับไปยังร้านและชุมชน โดยใช้ข้อมูลจริงและสิทธิ์ที่เหมาะสม

ยังไม่ตั้งตัวเลขเป้าหมายจนมีฐานข้อมูลพื้นที่นำร่องและงบดำเนินงาน

## 13. เรื่องที่ต้องตัดสินใจก่อนประเมินและเปิดจริง

| เรื่อง               | ข้อเสนอตั้งต้น / สิ่งที่ต้องระบุ                             | จังหวะที่ต้องตัดสินใจ            |
| -------------------- | ------------------------------------------------------------ | -------------------------------- |
| แบรนด์และโครงการเดิม | ชื่อใหม่หรือส่วนหนึ่งของโครงการที่มีอยู่                     | ก่อนออกแบบภาพลักษณ์และเชื่อมระบบ |
| พื้นที่และผู้ใช้     | ชุมชนนำร่องและคนไทย/ต่างชาติที่เน้น                          | ก่อนจัดทำเนื้อหาและทดสอบต้นแบบ   |
| ประเภทบริการแรก      | เสนอเริ่มกิจกรรมชุมชนและสินค้าจัดส่งได้; ที่พัก/รถมีแบบเฉพาะ | ก่อนประเมินงานธุรกรรม            |
| ผู้รับผิดชอบ         | ผู้ดูแลแพลตฟอร์ม ผู้ประสานงาน และผู้ช่วยเหลือลูกค้า          | ก่อนทดลองจริง                    |
| การรับเงินและรายรับ  | ผู้ให้บริการชำระเงิน ผู้รับเงิน รอบโอน และการจัดการข้อพิพาท  | ก่อนสร้างการเงิน                 |
| ค่าธรรมเนียม         | อัตรา ผู้จ่าย ภาษี/เอกสารที่เกี่ยวข้อง และวันที่มีผล         | ก่อนเปิดขาย                      |
| ยกเลิก/คืน           | เงื่อนไขรายประเภท ผู้รับภาระ และกรอบเวลาจัดการ               | ก่อนเปิดขาย                      |
| การจัดส่ง            | ผู้จัดส่ง พื้นที่ ค่าส่ง และข้อจำกัดสินค้า                   | ก่อนเปิดสินค้าประเภทนั้น         |
| เนื้อหาและข้อมูล     | ผู้ตรวจ สิทธิ์เผยแพร่ ระยะเก็บ และรอบทบทวน                   | ก่อนนำข้อมูลจริงเข้า             |
| งบและทีม             | งบเริ่มต้น งบรายเดือน ทีมดูแล และกำหนดเปิดที่ต้องการ         | ก่อนทำแผนเวลาและราคา             |

ก่อนเปิดให้บริการจริง ให้ตรวจข้อกำหนดที่ใช้กับประเภทธุรกิจและบริการที่เลือกโดยเฉพาะ เอกสารนี้เป็นข้อกำหนดผลิตภัณฑ์ ไม่ได้ตัดสินสถานะทางกฎหมายของธุรกิจ

## 14. งานออกแบบถัดไปที่นำไปทำต่อได้

สร้างต้นแบบคลิกทดลอง 3 เส้นทาง โดยใช้ข้อมูลจำลองติดป้ายชัดเจน:

1. นักท่องเที่ยวค้นพบชุมชน → จองกิจกรรม → ชำระจำลอง → ดูใบจอง
2. ลูกค้าเลือกสินค้าสองร้าน → ตรวจยอดแยก → ชำระจำลอง → ติดตามและขอคืนบางส่วน
3. ผู้ขายลงรายการ → รับงาน → ส่งมอบ → ดูรายรับ พร้อมคิวตรวจและช่วยเหลือของผู้ดูแล

ต้นแบบต้องมีกรณีรอยืนยัน ไม่มีที่ว่าง ชำระไม่สำเร็จ และยกเลิก เพื่อให้การทดสอบสะท้อนงานจริงก่อนเริ่มเชื่อมธุรกรรม
